# 4-14. 한 장씩 볼 때와 묶어서 볼 때는 다르다

## 문제

[4-1](4-1.md) 에서 "배치 32로 재면 안 된다"고 했다.
여기서 **왜인지를 숫자로 본다.**

## 실습

```bash
pytest -m lesson_4_14 -s
```

## 두 숫자가 반대로 움직인다

```text
    배치      전체 p50       표본당       첫 답까지       처리량/s
     1      0.003ms    0.003ms      0.003ms     347,827
     4      0.006ms    0.001ms      0.006ms     700,776
    16      0.015ms    0.001ms      0.015ms   1,037,816
    64      0.050ms    0.001ms      0.050ms   1,269,439
```

```text
표본당 시간      짧아진다   ← 처리량(throughput)
첫 답까지 시간   길어진다   ← 지연시간(latency)
```

배치는 **다 모여야 계산이 시작된다.**
배치 64로 돌리면 첫 번째 표본은 나머지 63개를 기다린다.

## 이득보다 대가가 크다

```text
처리량 이득     3.6배
첫 답까지 대가  17.5배
```

라인이 표본을 한 장씩 보내는 구조라면 **배치는 손해다.**

## 판정은 뒤의 숫자로 한다

```text
CRITICAL BATCH_MISSES_CYCLE_TIME
         배치 64에서 첫 답까지 0.05ms 걸린다. 사이클 타임은 0.01ms 다 —
         **표본당 시간이 짧아진 것과 제때 답하는 것은 다른 이야기다.**
```

표본당 시간으로 보면 여유가 넘친다. 첫 답까지로 보면 사이클을 놓친다.

## 배치가 항상 나쁜 것은 아니다

```text
INFO BATCH_THROUGHPUT_GAIN
     배치를 키우면 처리량이 3.6배가 된다.
     **여러 대를 한 서버가 맡는 구조라면 의미가 있다** —
     디바이스 한 대에서 한 장씩 보는 구조에서는 의미가 없다.
```

나쁜 것은 배치가 아니라 **배치로 잰 숫자를 디바이스 지연시간이라고 부르는 것**이다.

이 이야기는 [6-14](6-14.md) 에서 다시 나온다 — 클라우드 엔드포인트가 그 구조다.

## 기준은 언제나 표본 하나다

```python
BatchScaling(points=(BatchPoint(batch_size=1, ...), ...))
```

```text
InvariantViolation: 첫 지점은 배치 1이어야 한다. **기준은 표본 하나다.**
```

배치 4와 16만 재면 "4가 더 빠르다"까지만 알 수 있다.

## 자주 하는 실수

- **표본당 시간을 지연시간이라고 보고한다.** 사이클을 놓친다.
- **배치 1을 안 잰다.** 현장 숫자가 없는 것이다.
- **처리량이 좋아졌다고 배치를 늘린다.** 첫 답까지가 그만큼 길어진다.
