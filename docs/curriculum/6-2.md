# 6-2. Edge의 데이터를 S3에 모아라

## 문제

> **어디에 두느냐가 나중에 무엇을 꺼낼 수 있는지를 정한다.**

그리고 이 결정은 되돌리기 어렵다.
객체 100만 개를 다시 배치하려면 100만 번 복사해야 한다.

## 실습

```bash
pytest -m lesson_6_2 -s
```

## 두 가지 키

```text
평평한 키   uplinks/2026-05-23T09-14-22-DEV-02.jsonl
파티션 키   uplinks/kind=inference_log/device=DEV-02/date=2026-05-23/hour=09/part-00000.jsonl
```

"지난주 DEV-02 것만 줘"를 해 보면 차이가 드러난다.

```text
평평한 키   → **전부 훑어야 한다.** 객체가 100만 개면 100만 번이다.
파티션 키   → 접두어로 바로 좁혀진다.
```

```text
좁힌 접두어 : uplinks/kind=inference_log/device=DEV-02/date=2026-05-23/
훑는 객체   : 3개 (전체 12개 중)
```

`이름=값` 형태는 Athena·Glue·Spark 가 읽는 규칙이기도 하다.
파티션을 이렇게 짜 두면 나중에 쿼리 엔진이 그대로 알아본다.

## 순서대로여야 좁혀진다

```text
kind + device + date  → uplinks/kind=inference_log/device=DEV-02/date=2026-05-23/
device 만            → uplinks/
```

**앞이 안 맞으면 뒤는 못 좁힌다.**

```python
def prefix_for(self, **filters: str) -> str:
    for name in self.order:
        if name not in filters:
            break          # 중간이 비면 거기서 멈춘다
        parts.append(f"{name}={filters[name]}")
```

그래서 **자주 걸러내는 것을 앞에 둔다.** 파티션 순서가 곧 쿼리 패턴이다.
이걸 나중에 바꾸려면 전부 다시 써야 한다.

## 작은 파일 수만 개는 큰 파일 하나보다 비싸다

```text
4KiB × 50,000개  → ['LAKE_SMALL_FILES']
4MiB × 500개     → []
```

총량은 200GB 로 같다. 그런데 앞쪽은

```text
요청이 100배 나가고
목록 조회가 느려지고
쿼리 엔진이 파일을 5만 번 연다
```

```text
WARNING LAKE_SMALL_FILES
        평균 4.0KiB 짜리 객체가 50,000개다.
        **작은 파일 수만 개는 큰 파일 하나보다 훨씬 비싸다** —
        요청 수가 비용이고, 쿼리 엔진이 매번 파일을 연다.
```

그래서 현장에서는 작은 객체를 주기적으로 합친다(compaction).
**그 작업을 하려면 파티션이 잘 짜여 있어야 한다** — 여기서 한 결정이 거기까지 간다.

## 접두어 하나가 너무 넓어도 문제다

```text
WARNING LAKE_PREFIX_TOO_WIDE
        접두어 하나에 평균 40,000개가 들어 있다.
        파티션을 더 잘게 나눠야 목록 조회가 끝난다.
```

목록 조회는 1,000개씩 끊어 온다. 4만 개면 페이지를 40번 넘긴다.
시간(`hour`)까지 파티션에 넣는 이유다.

그리고 어댑터는 **paginator 를 쓴다.**

```python
paginator = self._s3.get_paginator("list_objects_v2")
for page in paginator.paginate(Bucket=self._bucket, Prefix=prefix):
    keys.extend(item["Key"] for item in page.get("Contents", []))
```

안 쓰면 1,000개에서 **조용히 잘린다.** 오류가 안 나서 더 위험하다.

## 키에 넣으면 안 되는 것

```text
a//b    a/../b    "a b"
```

객체 저장소마다 다르게 해석한다.
**여기서 막지 않으면 나중에 못 찾는 객체가 생긴다.**

빈 파티션도 마찬가지다 — `device=` 로 끝나는 접두어는 어떤 조회에도 안 걸린다.

## 진짜 S3 호출이다

```python
store.put(key, body)              # boto3 put_object
store.list_prefix(narrow)         # boto3 list_objects_v2 (paginated)
store.stats("uplinks/")           # 객체 수·크기·접두어 수
```

테스트는 moto 안에서 돌지만 **요청은 진짜 boto3 가 만든다.**
가짜 클라이언트를 세워 두고 "호출됐다"만 확인하면 API 이름이 틀려도 통과한다.

## 설계는 Domain, 실행은 Infrastructure

```text
KeyLayout           파티션을 어떻게 짤 것인가       ← Domain
KeyLayoutPolicy     이 설계로 나중에 살 수 있는가   ← Domain
S3ObjectStore       그 키로 실제로 넣고 꺼낸다      ← Infrastructure
```

`domain/fleet/object_key.py` 에는 **S3 라는 단어가 없다.**
객체 저장소가 무엇이든 같은 문제가 있기 때문이다.

## API

```http
POST /fleets/line3/lake
{
  "layout": {"prefix": "uplinks", "order": ["kind", "device", "date", "hour"]},
  "filters": {"kind": "inference_log", "device": "DEV-02", "date": "2026-05-23"}
}
```

응답에 **전체 객체 수와 좁힌 뒤 객체 수**가 함께 온다. 그 비가 곧 조회 비용이다.

## 자주 하는 실수

- **시각을 파일 이름에 넣는다.** 그러면 전부 훑어야 한다.
- **파티션 순서를 아무렇게나 정한다.** 앞이 안 맞으면 뒤는 못 좁힌다.
- **작은 파일을 그대로 둔다.** 총량보다 개수가 비용을 정한다.
- **paginator 를 안 쓴다.** 1,000개에서 조용히 잘린다.
