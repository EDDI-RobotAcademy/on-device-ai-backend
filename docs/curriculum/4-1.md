# 4-1. PC에서 돌아간다고 끝난 게 아니다

## 문제

모듈 3 에서 승인받은 모델이 있다. 정확도도 좋다.

그런데 **"이 모델 몇 ms 나와요?"** 라는 질문에는 아직 답할 수 없다.

같은 모델을 같은 기계에서 재도, **어떻게 재느냐에 따라 몇 배씩 달라지기 때문이다.**

## 실습

```bash
pytest -m lesson_4_1 -s
```

## 무엇을 보게 되는가

```text
측정 (PYTORCH/FP32)
  프로토콜 : warmup=10 runs=100 batch=1 threads=1
  p50 0.0306ms / p95 0.0316ms / p99 0.0321ms / 지터 1.03배
  파일 16,273B / 활성값 추정 8,400B
```

숫자 위에 **프로토콜이 한 줄 붙어 있다.** 이것이 이 실습의 전부다.

`0.0316ms` 만 적어 두면 다음 사람은 그 숫자를 재현할 수 없다.
워밍업을 안 했을 수도, 배치 32로 쟀을 수도, 코어를 8개 썼을 수도 있다.

## 어떻게 재면 틀리는가

```text
p50   0.3000ms  p95   2.5000ms  p99   3.1000ms  지터 8.33배

CRITICAL BENCH_NO_WARMUP (warmup)
         워밍업 0회. 첫 호출은 항상 느리다 — 메모리 할당, 커널 선택, 캐시가 비어 있다.
         그 숫자를 지연시간이라고 부를 수 없다.
WARNING  BENCH_TOO_FEW_RUNS (runs)
         10회로 p95 를 계산했다. 그 p95 는 다음에 재면 달라진다.
WARNING  BENCH_JITTER_HIGH (jitter)
         p95 가 p50 의 8.3배다. 가끔 크게 튄다.
```

| 실수 | 무슨 일이 일어나는가 |
|---|---|
| 워밍업 없이 첫 호출을 잰다 | 10배 느리게 나온다 |
| 스레드를 다 쓴다 | 디바이스에는 코어가 하나일 수 있다 |
| 배치를 32로 잰다 | 현장은 표본이 하나씩 들어온다 |
| 평균만 본다 | 20번에 한 번 튀는 것이 안 보인다 |

```text
CRITICAL BENCH_BATCHED (batch_size)
         배치 32로 쟀다. 이건 처리량(throughput)이지 지연시간(latency)이 아니다.
WARNING  BENCH_MULTI_THREAD (threads)
         스레드 8개로 쟀다. 디바이스에 코어가 그만큼 있는지 먼저 확인해야 한다.
```

## 평균이 없는 이유

`BenchmarkResult` 에는 `mean_ms` 가 없다. **일부러 뺐다.**

```python
@dataclass(frozen=True, slots=True)
class BenchmarkResult:
    p50_ms: float
    p95_ms: float
    p99_ms: float
    min_ms: float
    max_ms: float
```

현장에서 중요한 것은 '보통 얼마나 걸리는가'가 아니라 **'최악에 얼마나 걸리는가'** 다.
사이클 타임 30ms 는 평균 20ms 로 지켜지지 않는다. **p95 로 지킨다.**

## 승인받지 않은 모델은 최적화 대상이 아니다

```text
[ILLEGAL_STATE_TRANSITION] opt-not-accepted:
    승인받지 않은 모델은 최적화 대상이 아니다: 모듈 3 · 모델 승인 판정
```

순서가 있다. **쓸 수 있는지도 모르는 모델을 먼저 빠르게 만드는 것은 시간 낭비다.**

이 판정은 `BaselineModelRef.accepted` 한 줄로 들어온다.
모듈 3 의 `TrainingRun` 이 통째로 넘어오지 않는다 — Optimization Context 는 학습을 모른다.

```python
# application/optimization/baseline_mapper.py
return BaselineModelRef(
    model_version_id=str(run.model_version_id),
    parameter_count=profile.parameter_count,
    accuracy=matrix.accuracy,
    accepted=run.status is TrainingStatus.ACCEPTED,   # ← 게이트 한 줄
)
```

## 측정은 Infrastructure, 판정은 Domain

```text
Infrastructure   RuntimeLatencyBenchmarker      실제로 300번 돌린다
      ↓
Domain           BenchmarkResult                숫자 + 프로토콜
      ↓
Domain           BenchmarkPolicy.inspect()      이 측정을 믿어도 되는가
```

`BenchmarkPolicy` 는 torch 를 모른다. 그래서 **숫자를 손으로 만들어 시험할 수 있다.**

```python
naive = BenchmarkResult(
    protocol=MeasurementProtocol(warmup_runs=0, measured_runs=10),
    p50_ms=0.30, p95_ms=2.50, p99_ms=3.10, min_ms=0.28, max_ms=3.40,
)
assert "BENCH_NO_WARMUP" in {f.code for f in BenchmarkPolicy().inspect(naive)}
```

## API

```http
POST /optimization-runs
{ "run_id": "opt-power", "training_run_id": "run-opt" }

POST /optimization-runs/opt-power/baseline
{ "protocol": { "warmup_runs": 30, "measured_runs": 300, "batch_size": 1, "threads": 1 } }
```

응답에 `protocol` 문자열이 그대로 들어 있다. 숫자만 돌려주지 않는다.

## 자주 하는 실수

- **첫 호출을 잰다.** 그 숫자는 지연시간이 아니라 초기화 시간이다.
- **평균만 보고한다.** 20번에 한 번 사이클을 넘기는 모델이 통과한다.
- **배치로 재고 지연시간이라 부른다.** 처리량과 지연시간은 다른 것이다.
- **기준을 안 재고 최적화한다.** '빨라졌다'고 말할 근거가 없어진다.
