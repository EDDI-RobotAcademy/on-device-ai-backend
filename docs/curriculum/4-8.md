# 4-8. 정확도와 Latency를 직접 싸움 붙여라

## 문제

여섯 개의 후보가 있다. 각각 무엇을 주고 무엇을 받았는지 **한 표에 놓는다.**

표가 없으면 "빨라졌습니다"만 남고 무엇을 잃었는지는 아무도 모른다.

## 실습

```bash
pytest -m lesson_4_8 -s
```

## 무엇을 보게 되는가

```text
후보                        크기   p95(ms)      배속      정확도   macroR      Δ정확도
----------------------------------------------------------------------------
PYTORCH/FP32           15.9K    0.0312       —   1.0000   1.0000         —  (기준)
TORCHSCRIPT/FP32       18.0K    0.0209   1.49x   1.0000   1.0000   -0.0000
ONNX/FP32              13.8K    0.0083   3.74x   1.0000   1.0000   -0.0000
TFLITE/FP32            16.4K    0.0031  10.11x   1.0000   1.0000   -0.0000
TFLITE/FP16            11.4K    0.0030  10.24x   1.0000   1.0000   -0.0000
TFLITE/INT8             9.3K    0.0038   8.30x   1.0000   1.0000   -0.0000

  가장 빠름   : TFLITE/FP16
  가장 작음   : TFLITE/INT8
  가장 정확함 : PYTORCH/FP32
```

**셋이 서로 다르다.**

'최적'이라는 말은 이 표 앞에서 뜻을 잃는다.
**무엇을 기준으로 최적인지 먼저 말해야 한다.**

## 더 작게 만들었는데 더 느려졌다

```text
후보                    크기   p50(ms)   p95(ms)
FP32             16,780B    0.0030    0.0031
FP16             11,724B    0.0030    0.0030
INT8              9,512B    0.0036    0.0038
```

INT8 이 FP32 보다 **작다**(9,512 < 16,780). 그런데 **더 느리다**(0.0038 > 0.0031).

이 CPU 에는 정수 연산을 몰아 처리하는 유닛이 없다.
그래서 INT8 로 저장한 값을 **매번 실수로 되돌린 뒤** 계산한다.
그 역양자화 비용이 계산 이득보다 크다.

> **"양자화하면 빨라진다"는 문장에는 '하드웨어가 그것을 지원할 때'가 빠져 있다.**

드문 일이 아니다. 특히 작은 모델에서 INT8 은 자주 여기 들어온다.

```python
@property
def slower_than_baseline(self) -> tuple[OptimizationCandidate, ...]:
    """최적화했는데 오히려 느려진 후보들."""
```

Domain 이 이 경우를 **이름 붙여 갖고 있다.** 표에서 눈으로 찾지 않아도 된다.

## 지배당한 후보는 볼 필요가 없다

```text
파레토 전선 : TFLITE/FP16
```

```python
@property
def pareto_front(self) -> tuple[OptimizationCandidate, ...]:
    """다른 후보에게 **모든 면에서** 지지 않는 후보들.

    더 빠르면서 더 정확한 후보가 있으면 그 후보는 볼 필요가 없다.
    """
```

기준 모델(PYTORCH/FP32)은 전선에서 빠졌다.
더 빠르면서 정확도가 같은 후보가 있기 때문이다.

정확도가 전부 같은 이 데이터에서는 전선이 하나로 좁혀진다.
정확도가 갈리는 모델에서는 전선에 여러 후보가 남고, **그때부터 예산이 필요해진다.**

## 남은 여유는 값어치가 없다

```text
TFLITE/FP16        p95 0.0030ms
PYTORCH/FP32       p95 0.0312ms
```

두 후보의 차이는 0.03ms 다.
**설비 사이클이 30ms 라면 이 차이는 아무 값어치가 없다.**

예산을 이미 만족한 뒤에 남은 여유는 성능이 아니다.
그 여유를 얻으려고 정확도를 내줬다면 **그것은 손해다.**

이 문장이 [4-10](4-10.md) 의 선택 규칙이 된다.

## 같은 조합은 하나만 남는다

두 번 변환해도 표에는 한 줄이다.

```python
self._candidates[candidate.label] = candidate   # label = "ONNX/FP32"
```

같은 `(경로, 정밀도)` 가 두 줄로 남으면 표가 거짓말을 한다.
어느 쪽 숫자가 맞는지 아무도 모르게 된다.

## 이 표에 들어오려면

```text
1. 내보냈고        (ModelArtifact)
2. 대조했고        (NumericalEquivalence)
3. 쟀고            (BenchmarkResult)
4. 다시 평가했다   (ArtifactAccuracy)
```

**'변환 성공' 만으로는 후보가 되지 않는다.**
`OptimizationCandidate` 는 이 넷을 한 묶음으로 요구한다.

## API

```http
GET /optimization-runs/opt-power/tradeoff
```

```json
{
  "fastest": "TFLITE/FP16",
  "smallest": "TFLITE/INT8",
  "most_accurate": "PYTORCH/FP32",
  "slower_than_baseline": [],
  "pareto_front": ["TFLITE/FP16"],
  "report": "후보 ... (표 전체)"
}
```

## 자주 하는 실수

- **속도만 보고한다.** 무엇을 내줬는지가 사라진다.
- **기준 없이 배속을 말한다.** 무엇에 비해 3배인지 모른다.
- **가장 빠른 것을 고른다.** 예산을 넘겼는지, 여유가 남았는지 안 본다.
- **정확도가 같다고 아무거나 고른다.** 크기·RAM·런타임 요구가 다르다.
