# 5-12. 디바이스에서 도는 추론 파이프라인을 완성하라

## 문제

지금까지 모듈 5 는 **로그를 읽는 쪽**만 봤다.
그 로그를 만드는 쪽, 디바이스 안에서 실제로 도는 순서는 다섯 단계다.

```text
입력 수집 → 전처리 → 추론 → 후처리 → 알람/저장
```

다섯 단계 전부에 실패 방식이 있고,
**대부분의 현장 사고는 추론이 아닌 곳에서 난다.**

## 실습

```bash
pytest -m lesson_5_12 -s
```

## 실제로 돌려 보면

```text
[DEV-01] 입력 (30, 6) / 10s 간격 / 열 6개 / 라벨 ('FAULT', 'OVERLOAD', 'NORMAL')
단계               시도        성공          빠짐          시간
  ACQUIRE      34,560 →  34,560  ( 0.00% 빠짐)      55.2ms
  PREPROCESS   11,511 →   9,792  (14.93% 빠짐)       6.2ms  [배치 경계를 넘는 창 1719]
  INFER         9,792 →   9,792  ( 0.00% 빠짐)      14.2ms
  POSTPROCESS   9,792 →   9,511  ( 2.87% 빠짐)       0.0ms  [확신 부족 281]
  EMIT          9,511 →   9,511  ( 0.00% 빠짐)     110.2ms
  센서 34,560표본 → 판단 기회 11,511건 → 답 9,511건 (82.6%)
```

## 이 실습의 본론

```text
추론 성공률    100.0%
끝까지 간 비율  82.6%
```

**"모델은 잘 돕니다"가 맞는 말이면서 동시에 쓸모없는 말인 이유다.**
현장에서 사라진 판단은 추론이 아니라 그 앞뒤에서 사라졌다.

## 이유를 안 적으면 고칠 수 없다

```text
PREPROCESS   배치 경계를 넘는 창 1,719
POSTPROCESS  확신 부족 281
```

"1,719건 실패"로는 아무것도 못 한다.
**"배치 경계를 넘는 창 1,719건"이어야 고칠 수 있다.**

배치가 바뀌면 제품이 바뀐다. 한 창에 두 제품이 섞이면
모델은 학습 때 본 적 없는 조합을 본다 ([1-8](1-8.md), [3-4](3-4.md)).
**에러는 안 난다** — 그래서 여기서 세어 두지 않으면 아무도 모른다.

## 계약은 배포 시점에 대조한다

```python
PipelineContract(
    input_shape=(30, 6),
    sample_interval_seconds=10.0,   # **모델의 일부다**
    feature_fields=(...),
    normalization={...},
    class_labels=("FAULT", "OVERLOAD", "NORMAL"),
)
```

```text
CRITICAL PIPE_CONTRACT_MISMATCH
         학습 때의 계약과 다르다: 표본 간격 10s → 30s.
         **아무 에러도 안 난다.** 모델은 다른 것을 보면서
         그럴듯한 답을 계속 낸다 — 현장에서만 틀린다.
```

[5-1](5-1.md) 에서 만난 그 사고다. 실행 중에 알아채는 것은 이미 늦다.

## 순서는 불변식이다

```text
InvariantViolation: 단계가 순서대로가 아니다.
                    **추론 뒤에 전처리를 하는 파이프라인은 없다.**
```

## 자주 하는 실수

- **추론 성공률만 본다.** 끝까지 간 비율이 진짜 숫자다.
- **빠진 건수만 센다.** 이유를 안 적으면 못 고친다.
- **계약을 배포 뒤에 확인한다.** 그때는 이미 틀린 답이 나갔다.
- **후처리를 안 만든다.** 확신 없는 판단이 그대로 알람이 된다.
