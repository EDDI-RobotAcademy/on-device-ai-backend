# 2-4. 잘못된 Label 하나가 모델 전체를 망친다

## 문제

모듈 1(실습 1-6)에서는 이렇게 물었다.

> 라벨의 **정의**가 있는가? 사람들이 **합의**했는가?

여기서는 다른 것을 묻는다.

> 붙여 놓은 라벨이 실제 데이터와 **모순되지 않는가?**

정의가 있고 합의도 했는데, 실제로 붙은 라벨이 그 정의를 어길 수 있다.

## 라벨 오류는 데이터만 봐서는 찾을 수 없다

```bash
pytest -m lesson_2_4 -s
```

규칙 없이 검사하면:

```text
[LABEL_QUALITY] 60.0 (D)  FAILED
  - CRITICAL LABEL_NO_CONSISTENCY_RULE (rules) 라벨 일관성 규칙이 하나도 없다.
```

**'라벨 오류 0건'이 나온다. 찾을 방법이 없었으니 당연하다.**
그 0건은 근거가 아니다. 그래서 규칙이 없다는 사실 자체를 CRITICAL 로 잡는다.

## 규칙은 현장에서 받아 적는다

```python
LabelConsistencyRule(
    label="FAULT",
    field_name="active_power_kw",
    expected_max=30.0,
    description="보호 계전기가 동작하면 부하가 실제로 차단된다",
)
```

이 세 줄은 데이터에서 나오지 않는다. **설비 담당자에게서 나온다.**
실습 1-2 의 물리 범위(`ValueRange`)와 같은 자리에 있는 지식이다.

그리고 규칙에도 근거가 필요하다.

```python
LabelConsistencyRule(label="FAULT", field_name="active_power_kw", expected_max=30.0)
# InvariantViolation: 'FAULT' 규칙에 근거 설명이 없다. 나중에 아무도 이 숫자를 못 고친다.
```

숫자만 있고 이유가 없는 규칙은, 6개월 뒤 아무도 손대지 못하는 마법의 상수가 된다.

## 규칙을 넣으면 모순이 드러난다

```text
[LABEL_QUALITY] 59.8 (F)  FAILED
  - CRITICAL LABEL_RULE_VIOLATION (label) 현장 규칙과 모순되는 라벨이 180 건이다.
                                          [측정 0.02083 / 기준 0.005]
  - INFO     LABEL_VIOLATION_BY_CLASS (FAULT)    'FAULT' 라벨에서 규칙 위반 30 건.
  - INFO     LABEL_VIOLATION_BY_CLASS (NORMAL)   'NORMAL' 라벨에서 규칙 위반 120 건.
  - INFO     LABEL_VIOLATION_BY_CLASS (OVERLOAD) 'OVERLOAD' 라벨에서 규칙 위반 30 건.
  - CRITICAL LABEL_CONFLICT (label) 입력이 같은데 라벨이 다른 표본이 113 건이다.
```

- **FAULT 인데 부하가 정상** 30건 — 트립이 아니었거나, 라벨이 잘못 붙었다
- **NORMAL 인데 390kW** 120건 — 실습 2-3 에서 본 그 이상치다
- **OVERLOAD 인데 저부하** 30건

Finding 에 클래스별 내역까지 붙는다. 어느 작업자의 어느 판단을 다시 봐야 하는지가 나온다.

> 라벨이 틀렸거나, 규칙이 틀렸다. **둘 다 사람이 확인해야 한다.**
> 시스템은 어느 쪽인지 결정하지 않는다.

## 같은 입력에 다른 라벨

가장 치명적인 것이다.

```text
CRITICAL LABEL_CONFLICT  입력이 같은데 라벨이 다른 표본이 113 건 (42 개 묶음)이다.
                         모델은 이 모순을 학습할 수 없다.
```

모델 입장에서는 **같은 문제에 두 개의 정답**이 있는 것이다.
이 모순은 데이터를 아무리 늘려도 사라지지 않는다.

`max_conflict_ratio` 의 기본값이 `0.0` 인 이유다 — 단 한 건도 허용하지 않는다.

## 라벨 오류는 정확도 상한을 그 자리에서 깎는다

```text
라벨 오류 3% 가 만드는 천장
  규칙 위반   : 2.00%
  라벨 모순   : 1.00%
  정확도 상한 : 97.00%
```

모델을 아무리 키워도 이 선을 넘을 수 없다.
**'정확도 99% 목표'를 세우기 전에, 라벨이 그 숫자를 허용하는지부터 봐야 한다.**

```python
def accuracy_ceiling(self) -> float:
    return max(0.0, 1.0 - self.violation_ratio - self.conflict_ratio)
```

거친 근사다. 정확한 값을 주려는 것이 아니라
"라벨 오류 2% 는 정확도 2% 를 그냥 버리는 것"이라는 감각을 주기 위한 것이다.

## 왜 가중치가 가장 무거운가

```python
DEFAULT_WEIGHTS = {
    QualityDimension.LABEL_QUALITY: 0.25,   # 가장 무겁다
    QualityDimension.COMPLETENESS:  0.20,
    QualityDimension.VALIDITY:      0.20,
    QualityDimension.UNIQUENESS:    0.15,
    QualityDimension.BALANCE:       0.10,
    QualityDimension.NOISE:         0.10,
}
```

다른 축은 고칠 수 있다. 결측은 채우거나 잘라내고, 잡음은 필터링하고, 중복은 지운다.
**정답이 틀린 데이터는 아무리 고쳐도 그 이상 좋아지지 않는다.**

## 어떻게 고칠 것인가

| 상황 | 조치 |
|---|---|
| 라벨이 틀렸음이 확인됨 | `RELABEL` — 반드시 현장 확인을 거쳐 |
| 규칙이 틀렸음이 확인됨 | 규칙을 고치고 **재측정** |
| 같은 입력 다른 라벨 | `DROP_ROWS` 또는 `RELABEL` — 모순을 남겨 둘 수는 없다 |
| 판단 불가 | 해당 구간 `EXCLUDE_SEGMENT` |

## 자주 하는 실수

- **라벨은 정답이니까 맞다고 가정한다.** 라벨은 사람이 넣은 것이고, 사람은 틀린다.
- **규칙 없이 "라벨 오류 없음"을 보고한다.** 검사하지 않은 것이다.
- **모순되는 라벨을 발견하고 다수결로 자동 수정한다.** 다수가 틀렸을 수도 있다.
