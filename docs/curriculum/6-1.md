# 6-1. 디바이스에서 발생한 데이터를 Cloud로 보내라

## 문제

가장 먼저 정할 것은 "어떻게 보낼 것인가"가 아니라 **"무엇을 보낼 것인가"** 다.

전부 보내면 세 군데가 터진다.

```text
대역폭      현장 회선은 대개 좁다. 3,000대가 동시에 올리면 더 좁아진다.
비용        S3 저장은 싸지만 **전송과 요청 수는 싸지 않다.**
프라이버시  원본 신호에는 남기면 안 되는 것이 섞여 있을 수 있다.
```

앞의 둘은 되돌릴 수 있다. **세 번째는 되돌릴 수 없다.**

## 실습

```bash
pytest -m lesson_6_1 -s
```

## 무엇을 보게 되는가

```text
업링크 DEV-02  360건 7.0KiB  (오늘 누적 7.0KiB)
  → s3://ondevice-ai-lake/uplinks/kind=inference_log/device=DEV-02/date=2026-05-23/hour=09/part-00000.jsonl
```

360건을 **한 묶음으로** 올렸다. 한 건씩 올리지 않는다.

```text
WARNING UPLINK_TOO_CHATTY
        3건씩 올리고 있다. 요청 수가 곧 비용이고, 연결 수립이 곧 전력이다.
```

3건씩 올리면 하루에 수만 번 연결한다. 배터리도 요금도 거기서 나간다.

## 한 번 올라간 것은 지워지지 않는다

```text
CRITICAL UPLINK_FORBIDDEN_FIELD (operator_name)
         'operator_name' 는 올려서는 안 되는 열이다.
         **한 번 올라간 것은 지워도 지워지지 않는다** —
         백업·복제·로그·캐시에 남는다.
```

거절된 묶음은 **저장하지 않는다.** 그리고 그 사실을 응답으로 돌려준다.

```python
forbidden_fields: frozenset[str] = frozenset(
    {"operator_name", "employee_id", "badge_id", "phone", "email"}
)
```

그리고 이 검사는 **디바이스에서 먼저 돌아야 한다.**
서버까지 왔다는 건 이미 회선을 건넜다는 뜻이다.

## 무엇을 얼마나 올릴 것인가

```text
HEALTH_REPORT    아주 작고 주기적으로
INFERENCE_LOG    항상 (모듈 5 의 관측)
RAW_SAMPLE       골라서 (실습 6-4 의 재료)
INCIDENT         드물게, 원본을 붙여서
```

종류를 나누면 **종류마다 다른 예산과 다른 보관 기간**을 줄 수 있다.
하나로 뭉치면 그게 안 된다.

## 하루 전송 예산

```text
1회차 누적    70.3KiB  수락
2회차 누적   140.6KiB  수락
3회차 누적   140.6KiB  거절

CRITICAL UPLINK_OVER_DAILY_BUDGET
         하루 전송 예산을 넘는다.
         3,000대가 같이 넘으면 회선이 아니라 청구서가 먼저 터진다.
```

누적은 **DynamoDB 의 원자적 증가(ADD)** 로 센다.

```python
self._uplinks.update_item(
    Key={"device_key": f"{fleet_id}#{batch.device_id}", "date": date},
    UpdateExpression="ADD payload_bytes :b, record_count :r",
    ...
)
```

읽고-더하고-쓰면 **동시에 올라온 두 묶음 중 하나가 사라진다.**
수천 대가 동시에 올린다 — 그 경합은 이론이 아니다.

## 체크섬이 없으면 잘린 파일을 못 알아챈다

```text
WARNING UPLINK_NO_CHECKSUM
        체크섬이 없다. 좁은 회선에서 잘려 올라온 파일을
        온전한 것으로 착각하게 된다.
```

절반만 올라온 파일도 파일이다. 열면 열리고, 파싱도 된다.

## 등록되지 않은 디바이스는 올릴 수 없다

```text
[DEVICE_NOT_FOUND] DEV-999: 디바이스 'DEV-999' 가 이 플릿에 없다.
```

식별자만 있으면 아무나 올릴 수 있는 구멍을 만들지 않는다.
**등록되지 않은 디바이스의 데이터는 누구 것인지 모른다** — 계보가 거기서 끊긴다 (6-10).

## 올라왔다는 것이 곧 살아 있다는 뜻이다

```python
# 올라왔다는 것 자체가 살아 있다는 신호다.
fleet.report(batch.device_id, seen_at=batch.window_end)
```

별도의 헬스체크를 따로 받지 않아도 된다.
이 한 줄이 [6-11](6-11.md) 의 "몇 대가 연락이 안 되는가"를 채운다.

## AWS 는 여기까지만 온다

```text
domain/fleet/ports.py        ObjectStore, DeviceRegistry     ← boto3 없음
        ↓
infrastructure/aws/          S3ObjectStore, DynamoDeviceRegistry
```

Port 이름이 `ObjectStore` 이지 `S3Client` 가 아니다.
`tests/test_architecture.py` 가 매번 확인한다 — **domain/fleet 의 코드에는 AWS 어휘가 하나도 없다.**

## API

```http
POST /fleets/line3/uplinks
{
  "batch": {
    "device_id": "DEV-02",
    "kind": "INFERENCE_LOG",
    "window_start": "2026-05-23 09:00:00",
    "window_end": "2026-05-23 09:59:59",
    "record_count": 360,
    "payload_bytes": 7200,
    "checksum": "c0ffee",
    "fields": ["occurred_at", "predicted_label", "confidence", "latency_ms"]
  },
  "body_base64": "..."
}
```

202 로 돌아오고, 응답에 **수락 여부와 소견**이 함께 온다.

## 자주 하는 실수

- **전부 올린다.** 회선과 청구서가 먼저 터진다.
- **한 건씩 올린다.** 요청 수가 비용이고 연결이 전력이다.
- **개인정보를 서버에서 거른다.** 이미 회선을 건넌 뒤다.
- **누적을 읽고-더하고-쓴다.** 동시에 올라온 것이 사라진다.
