# 6-3. 수천 개의 디바이스 데이터를 하나로 관리하라

## 문제

디바이스가 3,000대면 **목록은 답이 아니다.** 아무도 3,000줄을 읽지 않는다.

## 실습

```bash
pytest -m lesson_6_3 -s
```

## 목록이 아니라 집계다

```text
디바이스 24대
----------------------------------------------------
  상태
    HEALTHY              24대  (100.0%)
  버전
    v1.0.0               24대  (100.0%)
  그룹
    line-b               14대
    line-a                8대
    pilot                 2대
```

**24대든 3,000대든 화면 크기가 같다.** 목록이면 그렇지 않다.

매일 아침 봐야 하는 질문은 셋이다.

```text
몇 대가 어느 버전으로 돌고 있는가
몇 대가 연락이 안 되는가
몇 대가 격리돼 있는가
```

## 키 설계가 여기서도 문제다

```text
PK = fleet_id     한 플릿의 디바이스를 한 번에 긁는다
SK = device_id    한 대를 바로 찾는다
```

이렇게 두면 "이 플릿의 전 디바이스"가 **Query 한 번**이다.

```python
response = self._devices.query(
    KeyConditionExpression=Key("fleet_id").eq(str(fleet_id))
)
```

PK 를 `device_id` 로 두면 같은 질문이 **Scan** 이 된다 —
1,000대면 1,000개를 다 읽고 필터링한다. S3 의 접두어와 같은 이야기다 ([6-2](6-2.md)).

그리고 결과가 1MB 를 넘으면 끊겨 온다. 그래서 `LastEvaluatedKey` 로 이어 받는다 —
안 하면 **조용히 일부만 가져온다.**

## 같은 식별자를 두 대가 쓰면

```text
[INVARIANT_VIOLATION] DEV-00: 'DEV-00' 가 이미 등록돼 있다.
    같은 식별자를 두 대가 쓰면 어느 쪽 데이터인지 영영 모른다.
```

현장에서 실제로 일어난다 — 이미지를 복제해 굽거나, 교체 장비에 옛 ID 를 넣는다.

## 버전은 디바이스가 말하는 것을 믿는다

```python
def report(self, device_id, *, seen_at, version=None, status=None) -> Device:
    """**버전은 디바이스가 말하는 것을 믿는다.**

    서버가 "보냈으니 올라갔겠지"라고 적어 두면,
    실제로 안 올라간 대수를 영영 모른다.
    """
```

이 규칙 하나가 [6-8](6-8.md) 의 실패율을 진짜로 만든다.
서버가 적어 두면 도달률 100% 가 늘 나오고, 그 숫자는 아무 뜻도 없다.

## 보고는 시간 순으로만

```text
[INVARIANT_VIOLATION] DEV-01: 'DEV-01' 의 보고가 직전보다 앞선 시각이다.
    디바이스 시계가 어긋났거나 재전송이다.
```

디바이스 시계는 실제로 어긋난다. 그대로 받으면 "마지막으로 본 시각"이 과거로 돌아간다.

## 그룹이 있어야 단계적 배포를 할 수 있다

```text
pilot      2대
line-a     8대
line-b    14대
```

그룹 없이 나누면 무작위가 된다.
**파일럿은 '아무 2대'가 아니라 '봐 줄 사람이 있는 2대'여야 한다.**

## 격리된 디바이스는 두 곳에서 빠진다

```python
@property
def is_reachable(self) -> bool:
    """지금 새 모델을 내보내면 받을 가능성이 있는가."""

@property
def is_trainable_source(self) -> bool:
    """이 디바이스의 데이터를 학습에 써도 되는가. (실습 6-4)"""
```

모듈 5 가 판단을 멈춰 세운 디바이스는

```text
배포 대상에서 빠진다   → 실패로 세면 실패율이 거짓말을 한다 (6-8)
학습 데이터에서 빠진다 → 이상한 상태에서 낸 판단을 다시 학습한다 (6-4)
```

## Aggregate 와 Registry 를 둘 다 두는 이유

```text
Fleet Aggregate    판단을 한다 — 다음 wave 를 정하려면 전체 상태를 봐야 한다
DeviceRegistry     수천 대를 담는다 — 조회는 이쪽이 담당한다
```

수만 대가 되면 Aggregate 하나가 전부를 드는 설계는 무너진다.
그때는 Fleet 을 사이트별로 쪼개고 집계를 읽기 전용 모델로 뺀다 —
**Registry Port 가 이미 그 자리를 잡아 두고 있다** ([6-11](6-11.md)).

## API

```http
GET  /fleets/line3
POST /fleets/line3/devices/DEV-03/status
{"status": "QUARANTINED", "note": "모듈 5 격리"}
```

## 자주 하는 실수

- **목록을 보여준다.** 3,000줄은 아무도 안 읽는다.
- **PK 를 device_id 로 둔다.** 플릿 조회가 Scan 이 된다.
- **페이지네이션을 안 한다.** 조용히 일부만 가져온다.
- **서버가 버전을 적어 둔다.** 실제 도달률을 영영 모른다.
