# 5-1. 모델을 처음으로 현장에 배포하라

## 문제

모듈 4 를 통과한 결과물이 있다. 파일도 있다. 그러면 올려도 되는가?

**파일이 준비된 것과 배포가 준비된 것은 다르다.**

## 실습

```bash
pytest -m lesson_5_1 -s
```

## 무엇을 보게 되는가

```text
배포 전 점검: PASSED
  대상 : 3라인 전력 감시 [DEVICE_GROUP · 3대]
  결과물 : mv-power-opt-cnn1d-s42-tflite-fp32 (TFLITE/FP32, 16,780B)
           기준 p95 0.0032ms / 정확도 1.0000
  **첫 배포다 — 되돌릴 곳이 없다.**

배포 dep-line3  3라인 전력 감시 [DEVICE_GROUP · 3대]  → DEPLOYED
--------------------------------------------------------------------------
  v1   2026-05-19 23:00:00  mv-power-opt-cnn1d-s42 (TFLITE/FP32)
```

## 네 가지가 함께 나간다

```text
결과물     모듈 4 가 고른 것
전처리     모듈 3 이 뽑은 정규화 통계
기준       모듈 4 가 잰 지연시간과 예측 분포
관측       배포와 **동시에** 시작하는 HealthWatch
```

마지막 것이 핵심이다. 관측을 나중에 켜면 그 사이 구간은 영영 비어 있다.
"언제부터 이상해졌죠?"에 "관측을 켠 뒤부터는요"라고 답하게 된다.

```python
# application/operations/deploy_model.py
commit(self._deployments, deployment, self._publisher)

# 관측은 배포와 **동시에** 시작한다.
watch = HealthWatch.open(
    watch_id, deployment_id,
    baseline_p95_ms=artifact.expected_p95_ms,
    baseline_mix=dict(artifact.expected_class_mix),
)
```

## 전처리는 모델의 일부다

```text
CRITICAL RELEASE_NO_PREPROCESSING (normalization)
         전처리 통계가 함께 나가지 않는다.
         **전처리는 모델의 일부다** — 디바이스가 다른 전처리를 하면
         변환 동등성을 아무리 확인해도 소용없다.
```

TFLite 파일에는 정규화 통계가 없다. 그것을 따로 안 보내면 디바이스가 다른 전처리를 한다.

실습 4-2 의 변환 동등성은 이걸 잡지 못한다.
**같은 입력을 넣지 않았기 때문이다.** 동등성은 "같은 입력에 같은 답"만 확인한다.

그리고 정규화 통계만의 이야기가 아니다.

```text
학습     10초 간격 × 30 표본 = 5분짜리 창
현장     30초 간격 × 30 표본 = 15분짜리 창
```

입력 모양은 `(30, 6)` 으로 똑같고 오류도 안 난다.
그런데 모델이 보는 것은 **다른 물리량**이다.
이 데이터에서 실제로 해 보면 OVERLOAD 예측 비율이 16.7% → 1.6% 로 무너진다.

**표본 간격도 모델의 일부다.** 현장 게이트웨이가 "트래픽을 줄이려고" 솎는 순간 이 일이 벌어진다.

## 기준 없이 배포하면 나중에 아무것도 말할 수 없다

```text
CRITICAL RELEASE_NO_BASELINE (baseline)
         기준 지연시간이나 기준 예측 분포가 없다.
         배포한 뒤에 '느려졌다' '이상해졌다'를 말할 근거가 없어진다.
```

`DeployedArtifactRef` 가 모듈 4 의 숫자를 들고 오는 이유다.

```python
expected_p95_ms: float = 0.0
"""최적화 때 잰 지연시간. 현장 지연시간을 여기에 견준다. (실습 5-5)"""

expected_class_mix: Mapping[str, float]
"""평가 때 각 클래스를 답한 비율. 현장 분포를 여기에 견준다. (실습 5-6)"""
```

## 첫 배포는 좁아야 한다

```text
CRITICAL RELEASE_FIRST_TOO_WIDE (ALL)
         첫 배포인데 1200대에 한 번에 올린다.
         **되돌릴 버전이 없다** — 문제가 나면 격리밖에 못 한다.
         몇 대로 먼저 확인한 뒤 넓힌다.  [측정 1200 / 기준 10]
```

| | 첫 배포 | 2차 배포 |
|---|---|---|
| 3대 | 통과 (INFO 만 남김) | 통과 |
| 1,200대 | **막힌다** | 통과 |

같은 결과물, 같은 대수인데 판정이 다르다.
**차이는 돌아갈 곳이 있느냐 하나다.**

## 선택 판정을 통과하지 않으면 대상이 아니다

```text
[NOT_DEPLOYABLE] dep-x:
    선택 판정을 통과하지 않은 결과물은 배포 대상이 아니다: 모듈 4 · 모델 선택 판정
```

예산 안에 드는지 확인하지 않은 결과물이 나가면
모듈 4 의 예산은 처음부터 없었던 것과 같다.

## 번역기가 세 곳에서 정보를 모은다

```python
# application/operations/artifact_mapper.py
선택 판정   모듈 4 의 OptimizationCertificate
기준 숫자   모듈 4 의 벤치마크 + 평가
전처리      모듈 3 의 TrainingDataRef   ← **결과물 파일에는 들어 있지 않다**
```

Operations Context 는 `OptimizationRun` 도 `TrainingRun` 도 모른다.
`DeployedArtifactRef` 라는 VO 하나로 번역되어 들어온다 (Anti-Corruption Layer).

## API

```http
POST /deployments
{
  "deployment_id": "dep-line3",
  "optimization_run_id": "opt-power",
  "training_run_id": "run-opt",
  "target": {"kind": "DEVICE_GROUP", "identifier": "LINE-3", "device_count": 3},
  "released_at": "2026-05-19 23:00:00"
}
```

응답에 배포 결과와 **점검 결과가 함께** 온다.
배포는 되지만 점검에 걸린 항목은 그대로 기록으로 남는다.

`released_at` 을 요청에 넣을 수 있다. 운영 기록은 데이터의 시각을 따라야 할 때가 있다 —
지난 로그를 다시 넣거나, 실습에서 4일치를 몇 초에 재생할 때가 그렇다.

## 자주 하는 실수

- **모델 파일만 보낸다.** 전처리가 빠지면 조용히 다른 모델이 된다.
- **관측을 나중에 켠다.** 그 사이 구간은 영영 비어 있다.
- **기준을 안 들고 간다.** 현장 숫자를 봐도 좋은지 나쁜지 말할 수 없다.
- **처음부터 전 라인에 올린다.** 되돌릴 곳이 없는 배포는 좁아야 한다.
