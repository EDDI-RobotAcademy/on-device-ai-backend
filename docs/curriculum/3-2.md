# 3-2. AI가 데이터를 계산하는 과정을 직접 뜯어보자

## 문제

`model.summary()` 를 찍어 본 적은 있을 것이다.
그 표를 **읽을 줄 아는가**가 이 실습이다.

층마다 무엇이 들어가서 무엇이 나오는지, 그 사이에 곱셈이 몇 번 일어나는지.
이 두 숫자가 모듈 4(최적화) 전체의 출발점이다.

## 실습

```bash
pytest -m lesson_3_2 -s
```

## 무엇을 보게 되는가

```text
layer               kind        output                      params          MACs
--------------------------------------------------------------------------------
features.0          Conv1d      (16, 30)                       496        14,400
features.1          ReLU        (16, 30)                         0             0
features.2          Conv1d      (32, 30)                     2,592        76,800
features.3          ReLU        (32, 30)                         0             0
pool                AdaptiveAvgPool1d (32, 1)                     0             0
dropout             Dropout     (32,)                            0             0
classifier          Linear      (3,)                            99            96
--------------------------------------------------------------------------------
합계                                                           3,187        91,296
  FP32 무게 12.4 KiB / 추론 1회 0.09 MMACs
```

## 두 숫자가 다른 것을 말한다

| 숫자 | 무엇을 결정하는가 | 모듈 4 에서 |
|---|---|---|
| `parameter_count` | 모델이 **들고 다녀야 하는 무게** | 메모리, 저장 공간, 양자화 대상 |
| `mac_count` | 추론 한 번의 **연산량** | 지연시간, 연산 병목 |

**둘은 비례하지 않는다.**

```text
가장 무거운 층(파라미터) : features.2  (2,592)
가장 바쁜 층(MAC)        : features.2  (76,800)
```

이 예에서는 같지만, 일반적으로는 다르다.

- **Conv 층**: 커널을 모든 위치에서 다시 쓴다 → 파라미터는 적고 연산은 많다
- **Linear 층**: 입력×출력만큼의 가중치를 한 번씩 쓴다 → 파라미터가 많고 연산은 그만큼

```text
conv    파라미터    500 / MAC  90,000   ← 바쁜 층
fc      파라미터  9,000 / MAC   9,000   ← 무거운 층
```

**메모리를 줄이려면 무거운 층을, 속도를 올리려면 바쁜 층을 봐야 한다.**
이 구분을 모르면 최적화를 엉뚱한 곳에 한다.

## 같은 입력, 다른 구조

```text
              params          MACs        FP32
CNN1D          3,187        91,296       12.4K
MLP           14,051        14,048       54.9K
```

MLP 는 `(30, 6)` 을 180개짜리 벡터로 **펴서** 첫 층에 통째로 연결한다.
파라미터가 4배 넘게 많은데도 **시간 순서는 보지 못한다.**

```python
class FlattenMLP(nn.Module):
    """시간 축을 펼쳐 버리는 모델.

    순서를 못 본다. 그래서 시계열에는 대개 부족하다.
    """
```

## 채널을 2배로 하면

```text
파라미터 3,187 → 11,779  (3.7배)
MAC      91,296 → 344,928 (3.8배)
```

Conv 파라미터는 `입력채널 × 출력채널 × 커널` 이므로,
둘 다 2배가 되면 대략 **4배**가 된다. 선형이 아니다.

"채널 좀 늘려 보죠"가 디바이스에서 어떤 의미인지 이 숫자가 말해 준다.

## 어떻게 세는가

```python
class TorchArchitectureProfiler:
    """dummy 입력을 한 번 흘려보내며 층마다 무엇이 나오는지 기록한다."""

    def profile(self, architecture):
        module = build_module(architecture)
        for name, layer in module.named_modules():
            if not name or list(layer.children()):
                continue  # 컨테이너는 건너뛴다. 잎(leaf) 층만 센다.
            handles.append(layer.register_forward_hook(make_hook(name, layer)))
        with torch.no_grad():
            module(torch.zeros(1, *architecture.input_spec.shape))
```

forward hook 으로 실제 출력을 붙잡는다. 계산식으로 추정하지 않는다 —
padding, stride, pooling 을 손으로 계산하면 반드시 틀린다.

## 설계 관점 — 명세와 구현

`domain/model/architecture.py` 에 **torch 라는 단어가 없다.**

```python
@dataclass(frozen=True, slots=True)
class ModelArchitecture:
    """어떤 모양의 계산을 할 것인가.

    PyTorch 의 nn.Module 이 아니다. 그것을 **만들기 위한 명세**다.
    """
    kind: ArchitectureKind
    input_spec: TensorSpec
    class_count: int
    hidden_channels: tuple[int, ...]
```

명세를 nn.Module 로 바꾸는 일은 `infrastructure/ml/torch_architecture.py` 의
`build_module()` 한 함수에서만 일어난다.

```bash
pytest tests/test_architecture.py -k PyTorch
# torch 가 infrastructure/ml 밖에서 쓰이면 실패한다
```

## 축 순서를 틀리면 조용히 이상해진다

```python
def forward(self, x: torch.Tensor) -> torch.Tensor:
    x = x.transpose(1, 2)  # (B, L, C) → (B, C, L)
```

데이터는 `(시간, 채널)` 순서인데 `Conv1d` 는 `(채널, 시간)` 을 기대한다.

**이 한 줄을 빼먹으면 '시간'을 '채널'로 읽으면서도 학습은 그냥 돌아간다.**
에러도 안 나고, loss 도 떨어진다. 성능만 이상하다.

## 자주 하는 실수

- **파라미터 수만 보고 "가볍다"고 판단한다.** Conv 는 파라미터가 적어도 느리다.
- **`model.summary()` 를 찍고 넘어간다.** 어느 층이 병목인지까지 읽어야 한다.
- **명세와 구현을 한 클래스에 섞는다.** 그러면 프레임워크를 못 바꾼다.
