# 4-10. 가장 빠른 모델이 아니라 가장 쓸 수 있는 모델을 선택하라

## 문제

모듈 4 의 게이트다. 모듈 1·2·3 과 같은 자리에 있다.

```text
모듈 1  이 데이터가 무엇인지 아는가
모듈 2  이 데이터가 쓸 만한가
모듈 3  이 모델이 쓸 만한가
모듈 4  이 모델을 **이 디바이스에** 올릴 수 있는가
```

선택 규칙은 한 줄이다.

> **예산을 만족하는 후보 중에서 가장 정확한 것.**

'가장 빠른 것'이 아니다. 예산을 이미 만족했다면 그보다 더 빠른 것은
아무 값어치가 없고, 그 속도를 얻으려고 내준 정확도만 손해다.

## 실습

```bash
pytest -m lesson_4_10 -s
```

## 무엇을 보게 되는가

```text
모델 선택: PASSED  (전력 감시 설비)
  예산 : p95 ≤ 1ms, 저장 ≤ 64KiB, 활성 ≤ 64KiB, macro recall ≥ 0.60, 정확도 하락 ≤ 2.00%
  목표 : ACCURACY
  선택 : TFLITE/FP32  p95 0.0030ms  정확도 1.0000

탈락 사유:
  ✗ PYTORCH/FP32
      CRITICAL SELECT_RUNTIME_NOT_DEPLOYABLE (PYTORCH/FP32)
               PYTORCH 는 파이썬 런타임을 요구한다. 디바이스에 파이썬이 있는지부터 확인해야 한다.
```

기준 모델은 언제나 가장 정확하다.
그런데 디바이스에 파이썬이 없으면 **그 정확도는 쓸 수 없는 정확도다.**

## 예산이 바뀌면 답이 바뀐다

```text
저장 64KiB   → 선택 TFLITE/FP32  (16,780B)
저장 15.9KiB → 선택 TFLITE/INT8  (방금 뽑힌 것이 안 들어가게 조였다)
```

**모델도, 측정값도 하나도 안 바뀌었다. 바뀐 것은 플래시 용량 한 줄이다.**

그래서 이 판정은 코드가 아니라 **설비가** 정한다.
`DeviceBudget` 이 요청 본문으로 들어오는 이유가 이것이다.

```python
@dataclass(frozen=True, slots=True)
class DeviceBudget:
    """디바이스가 허용하는 것.

    이 숫자들은 모델이 정하지 않는다. **설비와 하드웨어가 정한다.**
    사이클 타임 30ms, 플래시 256KiB, RAM 64KiB — 그런 식이다.
    """
    name: str
    latency_p95_ms: float
    storage_kib: float | None = None
    activation_kib: float | None = None
    min_macro_recall: float = 0.0
    max_accuracy_drop: float = 0.02
    max_class_recall_drop: float = 0.05
```

## 여섯 가지를 본다

| 검사 | 코드 | 무엇을 막는가 |
|---|---|---|
| 실행 경로 | `SELECT_RUNTIME_NOT_DEPLOYABLE` | 파이썬을 요구하는 런타임 |
| 지연시간 | `SELECT_OVER_LATENCY_BUDGET` | 사이클 타임 초과 |
| 저장 공간 | `SELECT_OVER_STORAGE_BUDGET` | 플래시 초과 |
| 활성값 | `SELECT_OVER_ACTIVATION_BUDGET` | **RAM 초과 (파일이 작아도 걸린다)** |
| 정확도 | `SELECT_ACCURACY_DROP` / `SELECT_BELOW_MACRO_RECALL` | 전체 성능 하락 |
| 클래스별 | `SELECT_CLASS_RECALL_DROP` | **한 클래스만 무너지는 경우** |

여기에 [4-2](4-2.md) 의 동등성 검사(`CONVERT_*`)가 그대로 얹힌다.
**대조하지 않은 후보는 아무리 빨라도 선택되지 않는다.**

## 잡음 수준의 차이로 고르지 않는다

이 모델은 3μs 대에서 돈다. 그 정도면 **다시 잴 때마다 순서가 바뀐다.**

```text
TFLITE/FP32   p95 0.0031ms
TFLITE/FP16   p95 0.0030ms   ← 다음에 재면 뒤집힌다
```

0.0030 과 0.0031 중에 고르는 것은 측정 잡음 중에 고르는 것이다.
그러면 같은 입력에 다른 답을 내는 선택이 된다.

```python
latency_tie_ratio: float = 0.05
# 이만큼 안쪽의 속도 차이는 **차이가 아니다.**
```

그래서 선택은 세 단계다.

```text
1. 정확도(macro recall → accuracy)가 가장 높은 후보들
2. 그중 가장 빠른 것의 5% 안에 드는 후보들
3. 그중 가장 작은 것        ← 플래시는 언제나 아쉽다
```

## 평균은 한 클래스의 붕괴를 숨긴다

```text
후보                        크기   p95(ms)      정확도   macroR      Δ정확도
TFLITE/FP32             9.8K    1.2000       0.9700   0.9500         —  (기준)
TFLITE/INT8             9.8K    1.2000       0.9620   0.8330   -0.0080

탈락 사유:
  ✗ TFLITE/INT8
      CRITICAL SELECT_CLASS_RECALL_DROP (TFLITE/INT8)
               'FAULT' 재현율이 35.00% 떨어졌다.
               전체 정확도는 거의 그대로인데 한 클래스만 무너진 것이다.
```

전체 정확도만 봤으면 통과시켰을 후보다 (−0.8%, 예산은 −2%).
클래스별로 보면 이 모델은 **설비 정지를 절반 가까이 놓친다.**

[4-7](4-7.md) 에서 본 상황이 여기서 실제로 막힌다.

## 예산을 만족하는 후보가 없으면 아무것도 고르지 않는다

```text
모델 선택: FAILED  (전력 감시 설비)
  예산 : p95 ≤ 0.0001ms, ...
  선택 : 없음 — 예산을 만족하는 후보가 하나도 없다

탈락 사유:
  ✗ PYTORCH/FP32   사이클 타임 안에 못 들어온다. [측정 0.03126 / 기준 0.0001]
  ✗ ONNX/FP32      사이클 타임 안에 못 들어온다. [측정 0.008129 / 기준 0.0001]
  ✗ TFLITE/FP32    사이클 타임 안에 못 들어온다. [측정 0.00325 / 기준 0.0001]
  ✗ TFLITE/INT8    사이클 타임 안에 못 들어온다. [측정 0.003708 / 기준 0.0001]
```

**가장 나은 것을 억지로 내놓지 않는다.** 그 순간 예산은 의미를 잃는다.

이때 할 일은 셋 중 하나다.
1. 모델을 더 줄인다 (모듈 3 으로 돌아간다)
2. 더 나은 하드웨어를 쓴다
3. 예산을 바꾼다 — **그리고 그것은 기록으로 남는 결정이어야 한다**

## 목표를 바꾸면 같은 예산에서도 다른 것을 고른다

```text
ACCURACY → TFLITE/FP32
SIZE     → TFLITE/INT8
```

```python
class SelectionObjective(Enum):
    ACCURACY = "ACCURACY"   # 예산 안에서 가장 정확한 것. 기본값이자 대개 옳은 선택.
    LATENCY  = "LATENCY"    # 여유를 남겨야 할 이유가 있을 때만.
    SIZE     = "SIZE"       # 플래시가 정말 모자랄 때.
```

**셋 모두 '예산을 만족하는 것 중에서' 라는 조건이 먼저 붙는다.**
목표는 통과한 후보들 사이의 우선순위일 뿐, 예산을 대신하지 않는다.

## 판정 뒤에는 후보를 몰래 추가할 수 없다

```text
[ILLEGAL_STATE_TRANSITION] opt-selection:
    SELECTED 상태에서는 '후보 추가' 을 할 수 없다.
    reopen(reason) 으로 판정을 되돌린 뒤 수정한다.
```

판정 뒤에 후보가 늘어나면 그 판정서는 무엇을 근거로 한 것인지 알 수 없게 된다.
되돌리려면 **이유를 남겨야 한다.** 모듈 1·2·3 의 `reopen` 과 같은 규칙이다.

## 판정서에는 근거가 함께 남는다

```python
@dataclass(frozen=True, slots=True)
class OptimizationCertificate:
    budget: DeviceBudget          # 어떤 예산으로
    objective: SelectionObjective # 무엇을 목표로
    verdict: Verdict
    selected_label: str | None
    verdicts: tuple[CandidateVerdict, ...]   # 탈락 후보와 그 이유 전부
    table: str                    # 그때의 비교표
```

**왜 이것을 골랐는가**와 **왜 저것을 안 골랐는가**가 같이 남는다.
6개월 뒤 "왜 ONNX 안 쓰고 TFLite 썼어요?"에 답할 수 있는 것은 이 기록뿐이다.

## 자주 하는 실수

- **가장 빠른 것을 고른다.** 남은 여유는 값어치가 없다.
- **예산 없이 '최적'을 말한다.** 기준 없는 최적은 정의되지 않는다.
- **전체 정확도만 본다.** 한 클래스의 붕괴를 놓친다.
- **RAM 예산을 안 건다.** 파일이 들어가도 못 돌리는 일이 잦다.
- **판정 근거를 안 남긴다.** 6개월 뒤 아무도 이유를 모른다.
