# 4-13. CPU와 메모리를 실제로 재라

## 문제

[4-5](4-5.md) 는 **파일 크기**를 쟀다. 9 KiB 까지 줄였다.
그런데 디바이스에서 프로세스를 죽이는 것은 파일 크기가 아니다.

```text
모델 파일     16 KiB
실행 중 RSS  838 MiB
```

> **"모델이 16KB 니까 256MB 보드에 들어갑니다"는 답이 아니다.**

## 실습

```bash
pytest -m lesson_4_13 -s
```

## 정직하게 밝혀 둘 것

여기서 재는 RSS 는 **파이썬 프로세스 전체**다.
인터프리터도, numpy 도, torch 도, tensorflow 도 그 안에 있다.
실제 보드는 TFLite 인터프리터만 올린다 — **절대값은 다르다.**

그래서 이 실습에서 믿을 수 있는 것은 **차이**다.

## 파일 크기와 실행 중 메모리는 다른 축이다

```text
TORCHSCRIPT/FP32   파일  17.4 KiB   실행 중  837.7 MiB  (49,259배)
ONNX/FP32          파일  13.8 KiB   실행 중  837.7 MiB  (61,996배)
TFLITE/FP32        파일  16.4 KiB   실행 중  837.7 MiB  (52,350배)
TFLITE/FP16        파일  11.4 KiB   실행 중  837.7 MiB  (74,926배)
TFLITE/INT8        파일   9.3 KiB   실행 중  837.7 MiB  (92,349배)
```

INT8 은 FP32 의 절반 이하다. **그런데 실행 중 메모리는 거의 같다.**

```text
WARNING RES_RUNTIME_DOMINATES
        실행 중 메모리가 모델 파일의 52350배다.
        **모델을 더 줄여도 이 숫자는 거의 안 움직인다** —
        여기서는 모델 경량화가 아니라 런타임 선택이 답이다.
```

## 유일하게 절대값을 믿을 수 있는 숫자

```text
배치     1  +   0.00 MiB
배치   256  +   1.66 MiB
배치 4096  +  30.17 MiB
```

배치를 키우면 **중간 결과를 담을 자리**가 그만큼 더 필요하다.
이것이 활성화 메모리다 — 파라미터와 별개로 잡히고, **임베디드에서는 이쪽이 먼저 터진다.**

## CPU 사용률이 1을 넘으면 코어를 여러 개 쓴 것이다

```text
CPU 시간   1,220.4 ms
벽시계     1,208.9 ms
사용률        1.01 코어
```

```text
CRITICAL RES_MULTI_CORE
         CPU 를 3.80 코어어치 썼다. 보드에는 1개뿐이다 —
         **여기서 잰 지연시간은 현장에서 그대로 나오지 않는다.**
```

노트북에서는 빠르게 나왔을 것이다. 보드에 코어가 하나면 그 숫자는 현장에서 4배가 된다 ([4-1](4-1.md)).

## 두 예산은 무게가 다르다

```text
지연시간이 예산을 넘으면 → 사이클을 놓친다
메모리가 예산을 넘으면   → **프로세스가 사라진다**
```

느려지는 것이 아니라 멈춘다.

## 자주 하는 실수

- **파일 크기로 보드를 고른다.** 실행 중 메모리가 수천 배다.
- **RSS 절대값을 그대로 보고한다.** 인터프리터가 섞여 있다.
- **배치를 키운 채로 잰다.** 활성화 메모리가 같이 커진다.
- **CPU 사용률을 안 본다.** 멀티코어로 잰 숫자를 디바이스로 가져간다.
