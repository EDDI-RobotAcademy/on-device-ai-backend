# 5-14. 트래픽을 나눠서 두 모델을 동시에 재라

## 문제

[5-9](5-9.md) 의 그림자(shadow)와 다르다. 그 차이가 이 실습의 전부다.

```text
그림자   새 모델도 돌리지만 **답은 안 쓴다.**
         안전하다. 대신 "현장이 어떻게 달라지는가"는 모른다.

A/B      트래픽의 일부에 **실제로 새 모델의 답을 쓴다.**
         현장 결과가 나온다. 대신 그 일부는 진짜 위험을 진다.
```

## 실습

```bash
pytest -m lesson_5_14 -s
```

## 그림자에서는 만들 수 없는 숫자

```text
[A/B] v1.2.0 90% vs v1.3.0 10% (device_id 기준)
  v1.2.0         9,000건 / 디바이스   9대  알람  20.00/1k  정밀도 0.600  p95   24.00ms
  v1.3.0         9,500건 / 디바이스   9대  알람  10.00/1k  정밀도 0.867  p95   25.00ms

  정밀도 +0.267  알람율 -10.00/1k  p95 +1.00ms
```

**사람이 확인해 준 정답은 실제로 답을 쓴 쪽에만 붙는다.**
그래서 그림자에서는 정밀도를 만들 수 없다.

## 그림자에 없는 규율 세 개

### 나누는 기준을 고정한다

```python
TrafficSplit(..., assignment_key="device_id")
```

요청마다 무작위로 나누면 같은 설비가 어제는 A, 오늘은 B 가 된다.
**차이가 모델 때문인지 설비 때문인지 영영 알 수 없다.**

### 양쪽에 충분한 표본과 디바이스가 있어야 한다

```text
CRITICAL AB_TOO_FEW_DEVICES
         후보가 디바이스 1대에서만 돌았다.
         **그 설비의 특성이 곧 결과가 된다.**

CRITICAL AB_NO_GROUND_TRUTH
         사람이 확인해 준 건이 4건뿐이다.
         **정답 없이는 '더 낫다'를 말할 수 없다.**
```

현장에서 정답이 붙는 비율은 12% 정도다 (O06) —
그래서 A/B 는 **정답을 모으는 절차와 함께** 설계해야 한다.

### 멈출 기준을 시작 전에 숫자로 적어 둔다

```python
SplitPolicy(stop_on_precision_drop=0.1, stop_on_latency_ratio=1.5)
```

```text
CRITICAL AB_STOP_PRECISION
         후보의 정밀도가 -0.300 낮다.
         **멈춤 기준을 넘었다 — 지금 되돌린다.**
         이 기준은 시작 전에 적어 두었기 때문에 지금 논쟁이 필요 없다.
```

"나빠 보이면 멈춘다"는 기준이 아니다.
적어 두지 않으면 "조금 더 지켜보자"가 반복되고, 그 사이 현장은 헛알람을 계속 받는다.

## 정확해도 느리면 못 쓴다

```text
CRITICAL AB_STOP_LATENCY
         후보의 p95 가 대조군의 2.00배다.
         **정확도가 좋아도 사이클을 놓치면 못 쓴다.**
```

## 배분이 어긋나면 공평하지 않다

```text
WARNING AB_ASSIGNMENT_SKEWED
        설계는 10% 인데 실제는 40.0% 다.
        **나누기가 고장났거나 한쪽 디바이스가 더 바쁘다.**
```

## 자주 하는 실수

- **매번 무작위로 나눈다.** 비교가 성립하지 않는다.
- **한 대에서만 돌린다.** 그 설비의 특성이 결과가 된다.
- **정답 없이 분포만 본다.** 어느 쪽이 옳은지 모른다.
- **멈출 기준을 나중에 정한다.** 그러면 못 멈춘다.
