# 1-3. 데이터의 정체부터 밝혀라

## 문제

`meter_id` 는 무엇인가?

- 이름이 `id` 로 끝난다 → 식별자?
- 값이 하나뿐이다 → 쓸모없는 열?
- 실은 "이 파일이 어느 계측기 것인가"를 적어 둔 메타데이터다.

데이터는 자기 **타입**은 말해 준다. 자기 **역할**은 말해 주지 않는다.
역할은 현장이 안다.

## 두 가지 타입

혼동하면 안 되는 구분이 있다.

```text
inferred_type   파일이 그렇게 보인다는 관측    (DatasetProfile)
DataSchema      우리가 그렇게 취급하겠다는 선언 (계약)
```

0과 1로 된 라벨은 관측하면 `INTEGER` 다. 그것이 `CATEGORY` 라는 것은 현장이 안다.

```bash
pytest -m lesson_1_3 -s
```

## 무엇을 보게 되는가

```text
스키마 초안 (raw)
field               type        role
--------------------------------------------
timestamp           TIMESTAMP   TIME_INDEX
meter_id            CATEGORY    IDENTIFIER      ← 틀렸다
batch_id            CATEGORY    GROUP
product_code        CATEGORY    METADATA
active_power_kw     REAL        FEATURE
...
condition           CATEGORY    LABEL
condition_review    CATEGORY    METADATA

확인 필요: product_code, condition_review, operator_note
```

추론기는 **이름과 타입만 보고 역할을 찍는다.** 정확할 리가 없다. 그것이 요점이다.

- 맞힌 것: `timestamp → TIME_INDEX`, `condition → LABEL`
  (이름과 타입만으로 알 수 있는 것들)
- 틀린 것: `meter_id → IDENTIFIER`
  (실제로는 값이 하나뿐인 설비 메타데이터. 입력에 넣으면 아무것도 배우지 못한다)

추론기는 확신하지 못한 필드를 **스스로 표시한다.** 여기가 대화가 시작되는 지점이다.

## FieldRole 이 정하는 것

역할은 이름표가 아니다. 이후 모든 단계의 동작을 바꾼다.

| 역할 | 이후에 무슨 일이 일어나는가 |
|------|------------------------------|
| `TIME_INDEX` | 시간축 검사(1-5)의 대상, 시간 기준 분할(1-8)의 기준 |
| `FEATURE` | 신호 검증(1-4)의 대상, 모델 입력 후보(1-7) |
| `LABEL` | 라벨 정의(1-6)의 대상. 입력에 넣으면 거부된다 |
| `GROUP` | 그룹 분할(1-8)의 단위. 입력에 넣으면 거부된다 |
| `IDENTIFIER` | 입력에 넣으면 거부된다 (모델이 ID 를 외운다) |
| `METADATA` | 기록용. 학습에 쓰지 않는다 |

역할을 잘못 정하면 그 오류가 8개 실습 뒤까지 따라간다.
그래서 추론 결과를 그대로 쓰지 않는다.

## 추론기는 Dataset 을 바꾸지 않는다

```python
class InferDataSchema:
    def execute(self, command): ...   # Dataset 을 저장하지 않는다
```

초안은 **사람이 보고 고칠 재료**일 뿐이다.
확정(`declare_schema`)만이 Aggregate 의 상태를 바꾼다.

이 구분을 흐리면 "AI가 스키마를 정해 줬다"는 말이 나오고,
그 순간 아무도 스키마를 책임지지 않게 된다.

## 스키마가 가진 불변식

```python
DataSchema(fields=(...))
```

- 시간축은 하나여야 한다. 두 개면 어느 쪽이 현장의 시간인지 알 수 없다.
- `TIME_INDEX` 인데 타입이 `TIMESTAMP` 가 아니면 거부한다.
- 수치형이 아닌 필드에 물리 범위를 줄 수 없다.
- 필드 이름은 중복될 수 없다.

이것들은 검사 함수가 아니라 **생성자에서** 걸린다.
잘못된 스키마 객체는 애초에 존재할 수 없다.

## 확정 후

```python
dataset.schema.time_index.name      # 'timestamp'
dataset.schema.label_field.name     # 'condition'
dataset.schema.group_fields         # (batch_id,)
len(dataset.schema.feature_fields)  # 6
```

이제 이후 모든 단계가 이 계약 위에서 돌아간다.
`InspectTimeAxis` 는 어느 열이 시간축인지 요청으로 받지 않는다. **스키마에서 읽는다.**

## API 로 해보기

```bash
curl localhost:8000/datasets/plant-power-raw/schema/draft     # 초안 받기
curl -X PUT localhost:8000/datasets/plant-power-raw/schema \
     -H 'Content-Type: application/json' -d @schema.json      # 확정
```

## 자주 하는 실수

- **추론 결과를 그대로 확정한다.** 이 실습이 존재하는 이유가 이것이다.
- **`condition_review` 를 FEATURE 로 넣는다.** 2차 작업자의 판단은 정답의 사본이다.
  넣으면 정확도가 폭등하고, 배포하면 그 열이 없다.
- **역할을 나중에 정하려고 미룬다.** 역할 없이 진행하면 1-7, 1-8 에서 전부 막힌다.
