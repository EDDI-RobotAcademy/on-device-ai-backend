# 5-13. 알람이 너무 많으면 아무도 안 본다

## 문제

모델이 이상을 잡았다고 알람이 되는 것이 아니다.
**알람은 사람이 반응할 수 있을 때만 알람이다.**

```text
1주차  알람이 뜬다. 사람이 달려간다.
2주차  하루 200번 뜬다. 몇 개만 본다.
3주차  소리를 끈다.
4주차  진짜 사고가 났을 때 아무도 못 봤다.
```

## 실습

```bash
pytest -m lesson_5_13 -s
```

## 규율 하나로 달라진다

```text
규율 없음 :  1,868건  (시간당  19.6건)
규율 있음 :    240건  (시간당   2.5건)
```

같은 모델, 같은 데이터다.
**잡는 능력이 달라진 것이 아니라 알리는 방식이 달라진 것이다.**

## 네 가지 규율

```python
AlertRule(
    alert_labels=("FAULT", "OVERLOAD"),
    dwell=3,                 # 3회 연속일 때만
    min_confidence=0.6,      # 확신이 부족하면 보류
    cooldown_seconds=300.0,  # 한 번 낸 뒤 5분은 조용히
    hourly_budget=12,        # 시간당 상한, 넘으면 **묶는다**
)
```

```text
[알람 규율] FAULT/OVERLOAD · 3회 연속 · 확신≥0.6 · 억제 300s · 시간당 12건
  원본 신호          2,066건
  확신 부족 보류       149건
  연속 확인 미달       326건
  억제 시간 내       1,351건
  상한으로 묶음          0건
  **실제 알람          240건**  (시간당 2.5건)
```

**원본 신호 수와 실제 알람 수를 함께 들고 다닌다.**
둘 중 하나만 보면 "잘 잡는다"와 "너무 많다"를 구분할 수 없다.

## 한 번 튄 것으로 사람을 부르지 않는다

```text
3회 연속 요구 : 알람 0건
1회로 충분    : 알람 1건
```

**현장 신호는 원래 가끔 튄다.**
센서 하나가 한 표본 흔들린 것으로 새벽 3시에 사람을 부르면,
다음 주에 그 알람은 꺼져 있다.

## 상한을 넘으면 버리지 않고 묶는다

**버리면 그 사건이 없던 일이 된다.** 묶으면 "이 시간에 N건"이 남는다.

그리고 상한에 걸렸다는 사실 자체가 "무언가 크게 잘못되었다"는 신호다 —
규율을 조이기 전에 모델과 현장을 먼저 봐야 한다.

## 양쪽 끝이 모두 위험하다

```text
CRITICAL ALERT_FATIGUE
         시간당 60.0건이다. **이 속도면 2주 안에 알람을 끈다.**
         알람을 줄이는 것은 편의가 아니라 안전이다.

WARNING ALERT_TOO_QUIET
        신호 2,066건 중 99.5% 를 눌렀다 (알람 1건).
        **규율이 너무 세면 알람도 조용해지고 사고도 조용해진다.**
```

조용한 쪽은 **비율**로 잡는다. 시간당 건수로는 못 잡는다 —
관측 구간이 짧으면 한 건만 나와도 "하루 14건"으로 환산되기 때문이다.

## 자주 하는 실수

- **모델이 이상이라고 하면 곧바로 알람을 낸다.** 2주면 꺼진다.
- **알람 수만 본다.** 원본 신호 수와 같이 봐야 한다.
- **상한을 넘은 것을 버린다.** 사건이 없던 일이 된다.
- **규율을 너무 세게 건다.** 사고도 같이 조용해진다.
