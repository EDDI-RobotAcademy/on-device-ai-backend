# 4-5. FP32 모델의 무게를 직접 측정하라

## 문제

파라미터 3,187개 × 4바이트 = **12,748바이트.**

계산은 쉽다. 그런데 파일은 그보다 크다.
이 실습에서 재는 것은 **그 차이**다.

차이를 모르면 다음 두 실습에서 "왜 이론만큼 안 줄었지?"에 답할 수 없다.

## 실습

```bash
pytest -m lesson_4_5 -s
```

## 무엇을 보게 되는가

```text
PYTORCH/FP32        16,273B = 가중치  12,748 + 오버헤드   3,525  (오버헤드 22%)
TORCHSCRIPT/FP32    18,409B = 가중치  12,748 + 오버헤드   5,661  (오버헤드 31%)
ONNX/FP32           14,169B = 가중치  12,748 + 오버헤드   1,421  (오버헤드 10%)
TFLITE/FP32         16,780B = 가중치  12,748 + 오버헤드   4,032  (오버헤드 24%)
TFLITE/FP16         11,724B = 가중치   6,374 + 오버헤드   5,350  (오버헤드 46%)
TFLITE/INT8          9,512B = 가중치   3,187 + 오버헤드   6,325  (오버헤드 66%)
```

**가중치는 어느 형식이든 12,748B 로 같다.**
달라지는 것은 그래프 구조·연산자 목록·메타데이터다.

## 이론값은 계산되고, 실제값은 측정된다

```python
@property
def theoretical_weight_bytes(self) -> int:
    """파라미터만 담았을 때의 크기."""
    return self.parameter_count * self.precision.bytes_per_weight

@property
def overhead_bytes(self) -> int:
    """가중치 외의 것 — 그래프 구조, 연산자 목록, 메타데이터."""
    return max(0, self.size_bytes - self.theoretical_weight_bytes)
```

`size_bytes` 는 **파일에서 잰다.**

```python
size_bytes=path.stat().st_size
```

계산한 값이 아니다. 이 구분이 이 실습의 요점이다.

## 작은 모델일수록 오버헤드의 몫이 크다

```text
TFLITE/FP32          16,780B (   16.4 KiB)  가중치  12,748B + 오버헤드   4,032B (24%)
TFLITE/FP32       4,004,032B ( 3910.2 KiB)  가중치 4,000,000B + 오버헤드   4,032B (0%)
```

같은 오버헤드 4,032B 인데,
파라미터 3,187개 모델에서는 **24%**, 100만개 모델에서는 **0.1%** 다.

**그래서 작은 모델을 INT8 로 줄여도 파일이 1/4 이 되지 않는다.**
줄어드는 것은 가중치 부분뿐이기 때문이다.

INT8 결과를 미리 보자.

```text
TFLITE/INT8   9,512B = 가중치 3,187 + 오버헤드 6,325   (오버헤드 66%)
```

**오버헤드가 가중치의 두 배다.** 16,780 → 9,512, 이론상 1/4 이 아니라 실제로는 57%.

## 정밀도가 이론 크기를 결정한다

```text
FP32    12,748B
FP16     6,374B
INT8     3,187B
```

```python
@property
def bytes_per_weight(self) -> int:
    return {"FP32": 4, "FP16": 2, "INT8": 1}[self.value]

@property
def is_quantized(self) -> bool:
    """정수로 바꿨는가. 바꿨다면 정확도 손실을 반드시 확인해야 한다."""
    return self is Precision.INT8
```

**FP16 은 값을 짧게 쓸 뿐 정수로 바꾸지 않는다. INT8 만 양자화다.**
이 구분이 [4-7](4-7.md) 에서 검증 방법을 갈라놓는다.

## 메모리는 두 종류다

```text
모델 파일 (플래시) :  16,273B
활성값 추정 (RAM)  :   8,400B
```

모델이 64KiB 플래시에 들어가도, **중간 결과가 RAM 을 넘으면 못 돌린다.**

```python
def _activation_bytes(self, architecture) -> int:
    """추론 중 잡아야 하는 중간 결과의 크기 (분석 추정).

    연속한 두 층의 출력이 동시에 살아 있다고 보는 이중 버퍼 근사다.
    실제 런타임은 더 아낄 수도, 더 쓸 수도 있다 — 그래서 '추정'이라고 적는다.
    """
```

임베디드에서는 이쪽이 먼저 막히는 일이 잦다.
실습 4-10 의 `DeviceBudget` 에 `activation_kib` 이 따로 있는 이유다.

## API

```http
GET /optimization-runs/opt-power/artifacts
```

후보마다 `size_bytes` / `theoretical_weight_bytes` / `overhead_bytes` 세 숫자가 함께 나온다.
세 개를 같이 봐야 "왜 안 줄었는가"에 답할 수 있다.

## 자주 하는 실수

- **파라미터 수로 크기를 보고한다.** 실제 파일은 그보다 크다.
- **파일 크기만 본다.** RAM 이 먼저 터진다.
- **양자화 이득을 이론값으로 약속한다.** 작은 모델에서는 절대 그만큼 안 나온다.
- **형식을 안 밝히고 '모델 크기'를 말한다.** 같은 모델도 형식마다 다르다.
