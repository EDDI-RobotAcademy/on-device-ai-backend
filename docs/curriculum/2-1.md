# 2-1. 깨끗한 데이터부터 의심하라

## 문제

모듈 1을 통과한 데이터를 가져온다.

- 스키마 ✓
- 시간축 ✓ (역순 0건, 중복 0건, 공백 0건)
- 신호 ✓
- 라벨 정의 ✓
- 분할 ✓
- 학습 설계 ✓
- **READY 판정까지 받았다.**

그리고 품질을 재 본다.

## 실습

```bash
pytest -m lesson_2_1 -s
```

## 무엇을 보게 되는가

```text
학습 착수 판정: PASSED_WITH_WARNINGS  (dirty)     ← 모듈 1
수행한 검사: LABEL_SPACE, PARTITION, SCHEMA, SIGNAL_PLAUSIBILITY,
             TIME_AXIS, TRAINING_SPEC

품질 여섯 축                                       ← 모듈 2
  COMPLETENESS      77.4 (C)  FAILED
  VALIDITY          61.6 (D)  FAILED
  LABEL_QUALITY     59.8 (F)  FAILED
  BALANCE           97.1 (A)  PASSED_WITH_WARNINGS
  NOISE             43.8 (F)  FAILED
  UNIQUENESS        85.9 (B)  FAILED
```

같은 파일이다. 여섯 축 중 다섯이 FAILED 다.

## 두 모듈은 다른 질문을 한다

| | 묻는 것 | 통과했다는 뜻 |
|---|---|---|
| **모듈 1** | 이 데이터가 **무엇인지 아는가** | 구조와 계약이 섰다 |
| **모듈 2** | 이 데이터가 **쓸 만한가** | 내용이 깨끗하다 |

앞의 질문에 답했다고 뒤의 질문에 답한 것이 아니다.
그래서 게이트가 둘이고, 통과 기록도 둘이다.

## 품질의 여섯 축

품질은 하나의 숫자가 아니다. **서로 다른 방식으로 망가진다.**

| 축 | 무엇이 잘못되었는가 | 실습 |
|---|---|---|
| `COMPLETENESS` | 값이 없다 | [2-2](2-2.md) |
| `VALIDITY` | 값이 말이 안 된다 | [2-3](2-3.md) |
| `LABEL_QUALITY` | 정답이 틀렸다 | [2-4](2-4.md) |
| `BALANCE` | 한쪽으로 쏠렸다 | [2-5](2-5.md) |
| `NOISE` | 신호보다 잡음이 크다 | [2-6](2-6.md) |
| `UNIQUENESS` | 같은 것을 반복해서 가르친다 | [2-7](2-7.md) |

축을 나누지 않으면 "품질이 나쁘다"까지만 말할 수 있고,
**무엇을 어떻게 고쳐야 하는지**는 말할 수 없다.

> 여섯 개의 실습이 하나의 개념(품질)의 여섯 축을 다룬다.
> 실습 제목마다 Domain 을 만든 것이 아니다. (CLAUDE.md §16, §22)

## 오염은 다른 검사의 결과까지 오염시킨다

이 실습에서 가장 중요한 장면이다. 오염된 데이터로 모듈 1의 **대표성 검사**를 돌려 본다.

```text
field                      PSI    coverage
------------------------------------------
voltage_v               3.0290     100.0%  ← 심각
temperature_c           0.0301     100.0%
```

- **전압 PSI 3.03** — 설비는 그대로다. 계측 배선에 잡음이 낀 것뿐인데
  드리프트가 일어난 것처럼 보인다. 이걸 보고 재학습을 결정하면 엉뚱한 대응이다.
- **온도 PSI 0.03** — 0.0 이 425개나 채워져 있는데 조용하다.
  분위수 구간 나누기는 한 점에 몰린 값을 옆 구간에 흡수해 버린다.

**드리프트 지표로는 품질 문제를 찾을 수 없다.** 한쪽은 거짓 경보를 내고,
다른 쪽은 침묵한다. 품질은 품질 도구로 봐야 한다.

그리고 순서도 여기서 나온다 — **품질을 먼저 정리해야 다른 판단도 신뢰할 수 있다.**

## 실습 데이터

`plant_power_quality_dirty.csv` 와 `plant_power_quality_clean.csv` 는
**구조가 완전히 같다.**

```python
assert list(clean.columns) == list(dirty.columns)
assert len(clean) == len(dirty) == 8640
assert clean["timestamp"].equals(dirty["timestamp"])
```

같은 설비, 같은 24시간, 같은 열. 다른 것은 내용뿐이다.
심어 놓은 오염 10종(Q01~Q10)은 `src/infrastructure/sample_data/plant_power_quality.py`
docstring 에 전부 적혀 있다.

## 설계 관점 — 두 Context 는 서로를 모른다

`domain/data_quality` 는 `domain/data` 를 **import 하지 않는다.**

```python
# application/data_quality/target_mapper.py — Anti-Corruption Layer
def assessment_target_from(dataset: Dataset) -> AssessmentTarget:
    ...
```

`Dataset` 이라는 남의 Aggregate 를 `AssessmentTarget`(원시 값만 담은 VO)으로 번역한다.
번역은 Application Layer 의 일이다.

이 규칙은 테스트가 지킨다.

```bash
pytest tests/test_architecture.py -k Bounded_Context
```

한 가지 더: 입력 필드는 스키마의 FEATURE 가 아니라 **학습 설계(1-7)**에서 가져온다.
품질은 "모델이 실제로 보게 될 열"에 대해 따져야 의미가 있기 때문이다.

## 자주 하는 실수

- **모듈 1을 통과했으니 됐다고 생각한다.** 이 실습 전체가 그 반례다.
- **`df.describe()` 를 보고 "깨끗해 보인다"고 판단한다.** 평균과 표준편차는
  0.0 으로 채워진 5% 를 거의 드러내지 않는다.
- **드리프트 지표로 품질을 감시한다.** 위에서 본 대로 양쪽으로 다 틀린다.
