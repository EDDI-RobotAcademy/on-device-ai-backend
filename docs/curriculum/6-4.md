# 6-4. Cloud에서 다시 학습 데이터를 만들어라

## 문제

**여기가 순환이 닫히는 지점이다.** 모듈 1 로 돌아간다.

그런데 올라온 것을 전부 쓰면 안 된다.

```text
격리된 디바이스의 데이터    이상한 상태에서 낸 판단이다 (실습 5-8)
드리프트 이전 구간          지금 고치려는 그 문제가 없던 시절이다 (실습 5-7)
라벨이 없는 구간            학습시킬 것이 없다 (실습 5-3)
한 디바이스에 몰린 데이터   그 디바이스의 버릇을 학습한다
```

## 실습

```bash
pytest -m lesson_6_4 -s
```

## 무엇을 보게 되는가

```text
학습 데이터셋 계획 build-2026-05-24
  구간   : 2026-05-22 00:00:00 ~ 2026-05-23 23:59:59 — 드리프트 시작 이후 구간 (실습 5-7)
  디바이스: 24대  (제외 0대)
  표본   : 21,600건  라벨 2,640건 (12.2%)
  라벨   : FAULT 140  NORMAL 1,900  OVERLOAD 600

판정: PASSED
  → s3://ondevice-ai-lake/datasets/build=build-2026-05-24/manifest.json
```

**구간을 왜 그렇게 잡았는지**가 함께 남는다.
드리프트 시작 이후만 쓴 것인지 전부 쓴 것인지가 결과를 가른다.

## 격리된 디바이스는 자동으로 빠진다

```text
  제외한 디바이스:
    ✗ DEV-05: QUARANTINED — 이상한 상태에서 낸 판단은 학습에 넣지 않는다 (실습 5-8)
    ✗ DEV-06: UNREACHABLE — ...
```

그리고 **뺐다는 사실과 이유가 기록에 남는다.**

```text
CRITICAL BUILD_UNEXPLAINED_EXCLUSION
         ['DEV-09'] 를 이유 없이 뺐다.
         **무엇을 뺐는지가 무엇을 넣었는지만큼 중요하다.**
```

빼는 것으로 결과를 바꿀 수 있기 때문이다.

## 현장 데이터가 많은 것과 학습할 수 있는 것은 다르다

```text
CRITICAL BUILD_TOO_FEW_LABELS
         라벨이 60건뿐이다 (0.5%).
         **현장 데이터가 많은 것과 학습할 수 있는 것은 다르다.**
```

표본은 12,000건이다. 그런데 학습시킬 수 있는 것은 60건이다.
나머지 11,940건은 정답을 모른다 ([5-3](5-3.md)).

## 한 디바이스가 절반을 넘으면

**자주 놓치는 실수다.**

```text
WARNING BUILD_DEVICE_DOMINATED
        'DEV-00' 한 대가 전체의 92.3% 를 차지한다.
        **새 모델은 그 디바이스의 버릇을 학습한다.**
```

회선이 좋은 디바이스, 가동률이 높은 라인에서 자연스럽게 생긴다.
표본 수를 맞추거나 가중치를 주지 않으면 그대로 편향이 된다.

그리고 이건 모듈 2 의 클래스 불균형([2-5](2-5.md))과 같은 문제가
**디바이스 축에서** 다시 나타난 것이다.

## 소수 클래스가 비면 그 클래스는 안 나아진다

```text
CRITICAL BUILD_MINORITY_LABEL_STARVED
         'FAULT' 라벨이 10건뿐이다.
         이 클래스는 재학습해도 나아지지 않는다 (실습 5-11).
```

실습 5-11 의 blocker 가 여기서 실제로 막는다.
**"재학습이 필요하다"와 "재학습할 수 있다"는 다르다.**

## 명세가 그대로 남는다

```json
{
  "build_id": "build-2026-05-24",
  "window": {
    "started_at": "2026-05-22 00:00:00",
    "ended_at": "2026-05-23 23:59:59",
    "reason": "드리프트 시작 이후 구간 (실습 5-7)"
  },
  "devices": ["DEV-00", "..."],
  "excluded": [{"device_id": "DEV-05", "reason": "QUARANTINED — ..."}],
  "label_distribution": {"NORMAL": 1900, "OVERLOAD": 600, "FAULT": 140}
}
```

이 파일이 **계보의 가장 위 칸**이다 ([6-10](6-10.md)).
안 남기면 6개월 뒤 "이 모델 뭐로 만들었죠?"에서 사슬이 끊긴다.

## 이 명세는 모듈 1 의 Dataset 이 아니다

```text
DatasetBuildSpec   어디서 무엇을 골랐는가        ← 모듈 6
Dataset            그 데이터가 쓸 만한가          ← 모듈 1·2
```

여기서 고른 뒤, 그 결과물이 **모듈 1 의 입력**이 된다.
그리고 모듈 1·2 의 게이트를 다시 통과해야 한다 — 현장 데이터라고 봐주지 않는다.

## API

```http
POST /fleets/line3/datasets
{
  "build_id": "build-2026-05-24",
  "window": {
    "started_at": "2026-05-22 00:00:00",
    "ended_at": "2026-05-23 23:59:59",
    "reason": "드리프트 시작 이후 구간"
  },
  "record_counts": {"DEV-00": 900, "...": 900},
  "labeled_counts": {"DEV-00": 110, "...": 110},
  "label_distribution": {"NORMAL": 1900, "OVERLOAD": 600, "FAULT": 140}
}
```

## 자주 하는 실수

- **올라온 것을 전부 쓴다.** 격리된 디바이스의 이상을 학습한다.
- **뺀 이유를 안 적는다.** 나중에 왜 없는지 아무도 모른다.
- **표본 수만 본다.** 라벨 수가 학습 가능한 양이다.
- **디바이스별 비율을 안 본다.** 한 대의 버릇을 배운다.
