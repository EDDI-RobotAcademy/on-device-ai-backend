# 6-11. 수천 대의 AI를 동시에 운영할 수 있는 구조를 만들어라

## 문제

규모가 커지면 질문 자체가 바뀐다.

```text
한 대     "이 모델이 잘 돌고 있는가"
수천 대   "**몇 대가** 어느 버전인가 / 연락이 안 되는가 / 실패하는가"
```

그리고 두 가지가 늘 참이다.

```text
1. 몇 대는 언제나 연락이 안 된다.
2. 버전은 절대 한 줄로 정렬되지 않는다.
```

## 실습

```bash
pytest -m lesson_6_11 -s
```

## 0을 요구하는 정책은 매일 실패한다

```text
3,000대 중 100대가 연락 안 됨 (3.3%)
  기준 0%  → ['FLEET_TOO_MANY_STALE']
  기준 5%  → []
```

꺼져 있고, 정비 중이고, 회선이 끊겼다. **그건 사고가 아니라 상태다.**

0을 요구하면 알람이 매일 울리고, 사람은 알람을 끈다 —
모듈 5-4 에서 본 그 실패다.

## version skew 는 0이 되지 않는다

```text
CRITICAL FLEET_VERSION_SKEW
         4종의 버전이 동시에 돌고 있다.
         문제가 생겨도 **어느 버전의 문제인지 가릴 수 없다.**

WARNING  FLEET_ROLLOUT_STALLED
         가장 많은 버전이 30.0% 뿐이다.
         배포가 중간에 멈춰 있다 — 끝내거나 되돌려야 한다.
```

**skew 를 0으로 만들려는 설계는 실패한다.**
할 수 있는 것은 얼마나 벌어져 있는지 아는 것뿐이다.

그리고 그 숫자가 다음 롤아웃의 입력이 된다 —
안 받은 디바이스만 다시 대상으로 잡으면 된다.

## 절반씩 갈린 상태가 가장 나쁘다

```text
v2.0.0  1,500대
v1.9.0  1,500대
```

**끝내거나 되돌려야 한다.** 이 상태로 두면

```text
현장 로그가 두 모델로 섞인다 (모듈 5 의 LOG_MIXED_VERSIONS)
문제가 나도 어느 쪽 문제인지 모른다
다음 배포가 어디서 시작해야 하는지 모른다
```

## 설치가 안 끝난 디바이스

```text
WARNING FLEET_NEVER_REPORTED
        42대가 등록만 되고 한 번도 올라온 적이 없다.
        대개 설치가 안 끝났거나 자격증명이 안 들어간 것이다.
```

**배포 대상 수를 세는 순간 이 42대가 실패로 잡힌다.**
등록됐다고 살아 있는 것이 아니다.

## 오래 연락 없는 디바이스를 표시한다

```python
def sweep_stale(self, *, now: str, stale_after: str, unreachable_after: str) -> int:
    """시각 비교만 한다. **Domain 은 시계를 모른다** — 기준 시각을 받아서 쓴다."""
```

표시된 디바이스는 두 곳에서 빠진다.

```text
배포 대상에서 (6-8)      실패로 세면 실패율이 거짓말을 한다
학습 데이터에서 (6-4)    연락 안 되는 디바이스의 옛 데이터를 다시 배운다
```

그리고 **훑기가 격리를 덮어쓰지 않는다.**

```python
if device.status in (DeviceStatus.QUARANTINED, DeviceStatus.RETIRED):
    continue
```

격리는 사람이 정한 상태다.
자동 훑기가 그것을 덮어쓰면 멈춰 세운 디바이스가 슬그머니 배포 대상으로 돌아온다.

## 3,000대도 같은 화면에 들어간다

```text
디바이스 3,000대
----------------------------------------------------
  상태
    HEALTHY           2,900대  ( 96.7%)
    STALE                80대  (  2.7%)
    UNREACHABLE          20대  (  0.7%)
  버전
    v2.0.0            2,700대  ( 90.0%)
    v1.9.0              300대  ( 10.0%)
  그룹
    line-a            1,500대
    line-b            1,500대
```

**줄 수가 대수에 비례하지 않는다.** 그게 수천 대를 다루는 유일한 방법이다.

## 이 설계의 한계 — 정직하게

```text
Fleet Aggregate 가 디바이스 목록을 통째로 들고 있다.
배포 판정이 전체 상태를 봐야 하기 때문이다 —
'몇 대가 어느 버전인가' 를 모르면 다음 wave 를 정할 수 없다.
```

**수만 대가 되면 이 설계는 무너진다.** 한 Aggregate 를 읽고 쓰는 데 수만 건이 오간다.

그때는 이렇게 바꾼다.

```text
Fleet 을 사이트별로 쪼갠다        line3, line4, plant-b …
집계를 읽기 전용 모델로 뺀다      DynamoDB 에서 직접 집계하거나 스트림으로 만든다
```

**`DeviceRegistry` Port 가 이미 그 자리를 잡아 두고 있다** — 지금도 조회는 그쪽이 담당한다.
바꿀 때 Domain 은 안 바뀐다.

## 부분 실패가 정상이다

```text
도달 83.3%
버전 2종 (v2.0.0 20대 / v1.0.0 4대)
```

이 모듈 전체의 전제다.
**완전한 상태를 목표로 삼는 대신, 불완전한 상태를 정확히 아는 것을 목표로 삼는다.**

## API

```http
GET  /fleets/line3
POST /fleets/line3/sweep
{
  "now": "2026-05-25 09:00:00",
  "stale_after": "2026-05-24 09:00:00",
  "unreachable_after": "2026-05-23 09:00:00"
}
```

## 자주 하는 실수

- **연락 두절 0%를 목표로 삼는다.** 매일 실패하고 알람이 꺼진다.
- **version skew 를 0으로 만들려 한다.** 배포가 영원히 안 끝난다.
- **절반씩 갈린 상태를 방치한다.** 가장 나쁜 상태다.
- **자동 훑기가 격리를 덮어쓴다.** 멈춰 세운 디바이스가 돌아온다.
