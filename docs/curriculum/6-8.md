# 6-8. OTA로 현장의 AI를 업데이트하라

## 문제

모듈 5 의 배포와 결정적으로 다른 점.

> **한 번에 다 안 간다.**

3,000대 중 몇 대는 꺼져 있고, 몇 대는 회선이 끊겼다.
"배포 완료"는 100% 가 아니라 **"받을 수 있는 것은 다 받았다"** 이다.

## 실습

```bash
pytest -m lesson_6_8 -s
```

## 단계로 나눈다

```text
롤아웃 ro-1  v2.0.0  → RUNNING
------------------------------------------------------------------------------
  wave-1           2대  성공     2  실패    0  미도달    0  대기    0  (실패율 0.0%)
  wave-2           8대  성공     6  실패    0  미도달    1  대기    1  (실패율 0.0%)
  wave-3          14대  성공    12  실패    0  미도달    2  대기    0  (실패율 0.0%)
------------------------------------------------------------------------------
  도달 20/24대 (83.3%)  실패 0  미도달 3
```

pilot 2대 → line-a 8대 → line-b 14대.
**그룹 순서가 곧 단계 순서다** ([6-3](6-3.md)).

첫 단계에서 문제가 나면 2대만 겪는다.

## 100%는 오지 않는다

**이 실습의 전제다.**

도달 83.3%. 나머지 4대는 꺼져 있거나 아직 답이 없다.
**100%를 기다리는 배포는 영원히 안 끝난다.**

```python
def complete(self, occurred_at: str) -> None:
    """남은 단계 없이 끝낸다.

    **100% 를 기다리지 않는다.** 받을 수 있는 것은 다 받았으면 끝난 것이다.
    """
```

## 실패율의 분모는 전체가 아니다

```text
6대 중 성공 2 · 실패 1 · 미도달 2 · 대기 1
  전체 기준 실패율 : 16.7%
  시도 기준 실패율 : 33.3%   ← 이쪽을 쓴다
```

```python
@property
def failure_ratio(self) -> float:
    """**분모가 전체가 아니라 '시도한 것'이다.**

    꺼져 있는 디바이스를 실패로 세면 실패율이 늘 높게 나오고,
    그러면 아무 배포도 통과하지 못한다.
    """
    return self.count(FAILED) / self.attempted if self.attempted else 0.0
```

네 가지를 구분한다.

| 결과 | 뜻 | 무엇의 문제인가 |
|---|---|---|
| SUCCEEDED | 받아서 설치했다 | — |
| FAILED | 받았는데 실패했다 | **모델일 수 있다** |
| UNREACHABLE | 연락이 안 됐다 | 회선·전원 |
| PENDING | 아직 아무 말이 없다 | 아직 모른다 |

**미도달과 대기는 시도가 아니다.**

## 실패가 기준을 넘으면 스스로 멈춘다

```text
CRITICAL OTA_FAILURE_RATE
         'wave-1' 에서 시도한 것 중 100.0% 가 실패했다. 다음 단계로 넘기지 않는다.
```

**사람이 대시보드를 보고 결정하기까지 기다리지 않는다.**
그 사이에도 나머지 22대로는 안 나간다 — 그게 단계로 나눈 이유다.

```text
[ROLLOUT_HALTED] ro-1: 멈춘 롤아웃이다: …
    되돌리거나(rollback), 이유를 붙여 재개(resume)한다.
```

## 응답이 안 왔으면 넘어가지 않는다

```text
CRITICAL OTA_NOT_ENOUGH_REPORTED
         10.0% 만 응답했다. 지금 다음 단계로 넘기면 단계를 나눈 의미가 없다.
```

2대 중 0대가 답했는데 8대로 넘어가면, 확인한 것이 아무것도 없다.

## 계획이 지켜야 하는 것

```text
단계가 커지는 순서여야 한다      큰 단계를 먼저 하면 확인할 것이 없다
첫 단계는 전체의 10% 이하        문제가 나도 그만큼만 겪는다
같은 디바이스가 두 단계에 없다   두 번 세면 실패율이 거짓말을 한다
```

작은 플릿에서는 10%가 0이 된다. 그래서 하한을 둔다.

```python
# 10% 로만 재면 작은 플릿에서는 상한이 0이 된다.
# 8대짜리 롤백에서 "첫 단계는 0대" 를 요구하는 것은 규칙이 아니라 버그다.
canary_limit = max(rules.min_canary_devices, sum(sizes) // 10)
```

## 대상은 지금 받을 수 있는 디바이스뿐이다

격리된 디바이스는 **처음부터 대상이 아니다.**
실패로 세면 실패율이 거짓말을 하고, 그러면 멀쩡한 배포가 막힌다.

## 알리는 것은 진짜, 응답은 합성

```text
알린다     실제 IoT Job 이 만들어진다 (moto 안에서 진짜 boto3 호출)
응답한다   합성이다 — moto 에 디바이스 쪽 API(iot-jobs-data)가 없다
```

Job 문서에는 **디바이스가 스스로 검증할 수 있는 것**이 들어간다.

```json
{
  "operation": "install-model",
  "version": "v2.0.0",
  "artifactUri": "s3://.../model.tflite",
  "checksum": "…",
  "sizeBytes": 11724,
  "normalization": {"active_power_kw": [147.8, 39.8]},
  "sampleIntervalSeconds": 10,
  "windowLength": 30
}
```

위치와 체크섬이 있어야 **잘려 도착한 파일을 스스로 걸러낸다.**
그리고 전처리가 함께 간다 ([6-6](6-6.md)).

시뮬레이터는 같은 디바이스에 **몇 번을 물어도 같은 답**을 한다.
실패했던 디바이스가 다음 조회에서 성공하면 실패율이 거짓말을 한다.

## 사람이 직접 멈출 수도 있다

```text
2026-05-24 14:00:00  중단 — 현장에서 알람이 늘었다는 연락
```

지표가 아직 안 넘었어도 멈출 수 있다.
**현장 연락이 지표보다 빠를 때가 있다.**

## API

```http
POST /fleets/line3/rollouts        → 202 (알린 것이지 도착한 것이 아니다)
POST /rollouts/ro-1/collect        → 이번 단계 결과
POST /rollouts/ro-1/advance        → 다음 단계
POST /rollouts/ro-1/halt           → 사람이 멈춤
```

## 자주 하는 실수

- **한 번에 전부에게 보낸다.** 문제가 나면 3,000대가 겪는다.
- **꺼진 디바이스를 실패로 센다.** 아무 배포도 통과하지 못한다.
- **응답을 안 기다리고 넘어간다.** 단계를 나눈 의미가 없다.
- **100%를 기다린다.** 배포가 영원히 안 끝난다.
