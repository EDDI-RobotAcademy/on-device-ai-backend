# 1-11. 수집 주기와 해상도를 직접 정하라

## 문제

이 결정은 되돌릴 수 없다.

```text
빠르게 잰 것은 나중에 느리게 만들 수 있다.
**느리게 잰 것은 나중에 빠르게 만들 수 없다.**
```

한 달을 30초 간격으로 모으고 나서 "10초가 필요했다"를 알게 되면
그 한 달은 없는 것이 된다.

## 실습

```bash
pytest -m lesson_1_11 -s
```

## 이론으로 정하지 않는다

원본을 **그 주기로 다시 뽑아 보고** 무엇이 사라지는지 센다.

```text
      주기       행 수      사건구간     사라짐          하루      판정
--------------------------------------------------------
     10s    12,960       197       0        0.5M      통과
     20s     6,480       126      33        0.3M      막힘
     30s     4,320        96      50        0.2M      막힘
     60s     2,160        87      77        0.1M      막힘
    300s       432        52     143        0.0M      막힘
```

30초로 모으면 사건 구간 50개가 **통째로 사라진다.**
사라진 사건은 라벨도 없고 학습에도 안 들어간다.
그리고 반년 뒤 "왜 이건 못 잡느냐"는 질문으로 돌아온다.

## 무엇을 잡을지 먼저 정해야 주기를 정할 수 있다

```python
SamplingDesignPolicy(target_event_seconds=60.0, min_samples_per_event=5.0)
```

`target_event_seconds` 는 코드가 정하는 숫자가 아니다. **현장이 정한다.**

> "30초짜리 트립은 놓쳐도 되지만 1분짜리는 안 된다"

이 합의가 없으면 주기 회의는 끝나지 않는다. 있으면 주기는 계산된다.

```text
'1분짜리는 반드시 잡는다'  → 10초 간격
'10분짜리만 잡으면 된다'   → 30초도 통과
```

## 나이퀴스트로는 부족하다

이론상 표본 2개면 주파수는 복원된다. 그러나 **모델이 보는 것은 주파수가 아니라 모양**이다.
점 두세 개로는 모양이 되지 않는다. 그래서 기본값이 5개다.

## 가장 빠른 것이 답이 아니다

```text
통과하는 것 중 가장 싼 설계: 10초 간격 / 30일 보관 (15.8 MiB)
```

**사건을 담을 수 있는 것 중 가장 싼 것**이 답이다.
이 데이터에서는 그게 마침 10초였을 뿐이다.

## 해상도도 같은 이야기다

```text
0.1 kW 단위 → 통과
50  kW 단위 → CRITICAL RESOLUTION_TOO_COARSE
```

50kW 단위로 반올림해 저장하면 그보다 작은 변화는 **영원히 사라진다.**
원본을 안 남겨 두면 되살릴 방법이 없다.

이미지에서는 이것이 "가는 균열이 리사이즈에서 뭉개진다"로 나타난다 ([3-11](3-11.md)).

## 비용은 한 대 기준이 아니다

```text
5초  : 31.6 MiB / 30일 / 1대  →  3,000대면 92 GiB
10초 : 15.8 MiB / 30일 / 1대  →  3,000대면 46 GiB
```

한 대만 보면 사소하다. **3,000대를 곱하면 사소하지 않다** (모듈 6).
"일단 빠르게 모으자"도 공짜가 아니다.

## 자주 하는 실수

- **주기부터 논한다.** 무엇을 잡을지 먼저 정해야 한다.
- **관측된 가장 짧은 사건을 기준으로 삼는다.** 1표본짜리 깜빡임까지 잡으려면 어떤 주기도 통과 못 한다.
- **저장 비용만 본다.** 사라진 사건은 돈으로 살 수 없다.
- **해상도를 나중에 정한다.** 굵게 저장한 값은 되살릴 수 없다.
