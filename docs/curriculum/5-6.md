# 5-6. Prediction Distribution의 변화를 추적하라

## 문제

**이 지표의 값어치는 하나다 — 정답이 없어도 잴 수 있다.**

정확도는 못 잰다 ([5-3](5-3.md)).
그런데 모델이 **무엇을 얼마나 답하고 있는지**는 셀 수 있다.

## 실습

```bash
pytest -m lesson_5_6 -s
```

## 기준부터 다시 잡아야 한다

```text
모듈 4 평가 데이터   FAULT 4.5%
현장 1일차            FAULT 0.8%
```

**평가 집합과 현장은 처음부터 다르다.**
평가 집합에는 사건이 골고루 들어 있고([3-8](3-8.md)), 현장은 대개 평온하기 때문이다.

이 상태로 두면 현장 분포는 **처음부터** 기준과 어긋나 있고, 진짜 변화가 그 어긋남에 묻힌다.

```text
기준 예측 분포 (현장 1일차로 재고정한 뒤)
  NORMAL       77.9%
  OVERLOAD     21.3%
  FAULT         0.8%
```

그래서 배포 직후 **아무 일도 없었던 구간**을 새 기준으로 못박는다.

```python
def rebaseline(self, mix: dict[str, float], reason: str) -> dict[str, float]:
    """기준 예측 분포를 현장 안정 구간으로 다시 잡는다.

    단, 그 구간이 정말 평온했는지는 사람이 확인해야 한다 —
    **이상한 구간을 기준으로 잡으면 그 이상이 정상이 된다.**
    """
```

이유가 필수다. **판정 기준을 바꾸는 일이기 때문이다.**
`BaselineReanchored` 사건으로 남는다 — 판정 결과보다 중요한 기록이다.

## 알람이 몇 배로 늘었는지 센다

```text
WARNING OPS_LABEL_SURGE (FAULT)
        'FAULT' 비율이 기준의 5.0배다.
        현장에 알람이 그만큼 더 울리고 있다는 뜻이다 — 사람이 곧 알람을 꺼 버린다.
        [측정 0.04201 / 기준 0.02524]
```

FAULT 예측이 0.8% → 4.2% 가 됐다.
**설비 정지 알람이 하루 5배로 울리고 있다.**

여기서 정확도는 여전히 모른다. 알 수 있는 것은 "무언가 달라졌다"까지다.
**그것만으로도 사람을 부르기에는 충분하다.**

## 확신도가 올라가도 안심할 수 없다

이 실습에서 가장 불편한 사실이다.

```text
평균 확신도    1일차 0.943 → 4일차 0.964     ← 올라갔다
실제 정확도    1일차 0.83  → 4일차 0.73      ← 떨어졌다
```

**모델은 자기가 틀린 줄 모른다.**

softmax 는 "이 셋 중에 뭐가 제일 큰가"를 말할 뿐,
"내가 이 입력을 본 적 있는가"를 말하지 않는다.
학습 때 본 적 없는 구간에서도 자신 있게 하나를 고른다.

| 신호 | 읽는 법 |
|---|---|
| 확신도가 내려갔다 | 모델이 헷갈린다 — 유용한 신호 |
| **확신도가 유지된다** | **안전의 근거가 못 된다** |

그래서 입력 분포를 따로 봐야 한다 ([5-7](5-7.md)).

## 분포가 크게 달라지면 둘 중 하나다

```text
클래스               건수       비율      평균확신      기준       차이
-----------------------------------------------------------------
NORMAL         1,230    41.0%     0.900    78.0%   -37.0%
FAULT          1,110    37.0%     0.800     1.0%   +36.0%
OVERLOAD         660    22.0%     0.850    21.0%    +1.0%

WARNING OPS_PREDICTION_SHIFT
        예측 분포가 기준과 37.0% 달라졌다.
        세상이 변했거나 모델이 무너졌다 — **둘 다 사람이 봐야 한다.**
```

```text
세상이 변했다   → 설비가 실제로 자주 서고 있다 (모델은 잘 하고 있다)
모델이 무너졌다 → 입력이 변해 엉뚱한 답을 하고 있다
```

확신도가 함께 내려갔다면 두 번째 쪽이다.
그래서 `OPS_CONFIDENCE_DROP` 과 `OPS_PREDICTION_SHIFT` 를 **같이** 본다.

## 한 클래스가 사라지면 그 클래스에 모델은 없는 것이다

```text
WARNING OPS_LABEL_VANISHED (FAULT)
        'FAULT' 을 현장에서 한 번도 예측하지 않았다.
        이 클래스에 대해서는 모델이 없는 것과 같다.
```

실습 3-9 의 `EVAL_CLASS_NEVER_PREDICTED` 가 **현장에서 다시 나타난 것**이다.
평가에서 잡았는데 현장에서 또 이렇게 되는 일이 있다.

놓치면 안 되는 클래스면 CRITICAL, 아니면 WARNING —
그 구분은 `critical_labels` 로 현장이 정한다.

## 총변동거리를 쓰는 이유

```python
def shift_from(self, baseline: Mapping[str, float]) -> float:
    """분포가 얼마나 달라졌는가 (총변동거리, 0~1).

    PSI 대신 이것을 쓰는 이유: **클래스가 몇 개 안 된다.**
    3개짜리 분포에 PSI 를 쓰면 한 칸이 비는 순간 무한대로 튄다.
    """
    return 0.5 * sum(abs(self.share_of(l) - baseline.get(l, 0.0)) for l in labels)
```

입력 채널은 연속값이라 PSI 가 맞고([5-7](5-7.md)), 예측은 클래스가 3개라 총변동거리가 맞다.
**지표는 데이터의 모양이 정한다.**

## 자주 하는 실수

- **평가 분포를 그대로 기준으로 쓴다.** 처음부터 어긋나 진짜 변화가 묻힌다.
- **이상한 구간으로 기준을 다시 잡는다.** 그 이상이 정상이 된다.
- **확신도가 높으니 괜찮다고 본다.** 모델은 자기가 틀린 줄 모른다.
- **분포만 본다.** 세상이 변한 건지 모델이 무너진 건지 구분하려면 입력도 봐야 한다.
