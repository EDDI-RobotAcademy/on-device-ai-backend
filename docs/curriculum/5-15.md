# 5-15. 파일로 보낼 것인가, 컨테이너로 보낼 것인가

## 문제

모듈 6 의 OTA 는 "모델 파일을 내려보낸다"를 전제로 한다.
**그 전제 자체가 선택이다.**

```text
모델 파일만    9 KiB. 회선이 좁아도 된다.
               대신 디바이스의 전처리·라벨 순서가 **이미 맞아야 한다.**

묶음(BUNDLE)   모델 + 전처리 명세 + 라벨. 런타임은 디바이스 것을 쓴다.

컨테이너       모델 + 런타임 + 전처리를 통째로.
               "내 노트북에서는 됐는데"가 사라진다.
               대신 수백 MiB 이고, 컨테이너가 도는 보드여야 한다.
```

## 실습

```bash
pytest -m lesson_5_15 -s
```

## 비교표

```text
[배포 방식] 컨테이너 가능 / 여유 2048 MiB / 회선 256 KiB/s / 3,000대
  MODEL_FILE       0.01 MiB  전송     0.0s  롤백     20s  플릿 총량    0.03 GiB
  BUNDLE           0.05 MiB  전송     0.2s  롤백     30s  플릿 총량    0.13 GiB
  CONTAINER      180.00 MiB  전송   720.0s  롤백    240s  플릿 총량  527.34 GiB
```

같은 모델을 보내는데 전송량이 2만 배 차이난다.
**3,000대를 곱하면 27 MiB 와 527 GiB 다** (모듈 6).

## 경계는 대개 여기다

```text
CRITICAL PKG_RUNTIME_UNSUPPORTED
         이 디바이스에는 컨테이너 런타임이 없다.
         **MCU/RTOS 에서는 선택지 자체가 아니다.**
```

여기서는 파일 배포만 가능하고, 그래서 전처리 일치를 사람이 지켜야 한다 —
그 부담이 곧 [5-12](5-12.md) 의 계약 대조다.

## 모델만 보내면 전처리는 안 간다

```text
WARNING PKG_PREPROCESSING_NOT_SHIPPED
        모델만 보낸다. 전처리와 라벨 순서는 디바이스에 이미 있는 것을 쓴다.
        **둘이 어긋나도 아무 에러가 안 난다.**
```

**선택의 대가는 나중에 절차로 돌아온다.**

## 저장 공간이 롤백 가능 여부를 정한다

```text
CRITICAL PKG_NO_STORAGE
         180 MiB 를 받으려면 360 MiB 가 필요하다 (여유 200 MiB).
         **옛 것을 지우고 받으면 되돌릴 곳이 없어진다** ([6-9](6-9.md)).
```

새 것을 받는 동안 **옛 것도 남아 있어야** 롤백이 된다. 그래서 2배가 필요하다.

## 되돌리는 시간이 곧 피해 크기다

```text
모델 파일     20s → 소견 없음
컨테이너     240s → PKG_ROLLBACK_SLOW
```

**빠른 롤백은 나중에 붙이는 기능이 아니라 배포 방식을 고를 때 함께 정해지는 성질이다.**

## 회선이 좁으면 컨테이너는 현실적이지 않다

```text
한 대에 96분 / 플릿 총량 527 GiB
```

**업데이트 중에도 라인은 돌고 있다.**
3,000대를 다 돌리는 데 몇 주가 걸리고, 그 사이 절반은 옛 모델이다 ([6-8](6-8.md)).

## 묶음이 그 중간이다

48 KiB 로 계약 불일치를 막는다. **현장에서 가장 자주 쓰는 절충이다.**

## 자주 하는 실수

- **컨테이너가 항상 안전하다고 생각한다.** MCU 에서는 못 돈다.
- **파일 배포를 고르고 계약 대조를 안 한다.** 조용히 틀린다.
- **저장 공간을 딱 맞게 잡는다.** 롤백이 사라진다.
- **전송 시간을 한 대 기준으로만 본다.** 3,000대면 몇 주다.
