# 1-7. AI가 먹을 수 있는 데이터로 다시 설계하라

## 문제

CSV 한 줄은 모델의 입력이 아니다.
모델의 입력은 **고정된 모양(shape)을 가진 텐서**다.

시계열이라면 "몇 초를 한 덩어리로 볼 것인가"를 정해야 그 모양이 결정된다.
그리고 그 숫자는 기술이 아니라 현장이 답한다.

> "이 설비에서 이상 징후는 몇 초 만에 드러나는가?"

## 여기서 정하는 것은 값이 아니라 계약이다

이 계약은 이후 학습·최적화·배포에서 **전부 다시 쓰인다.**

전처리 코드가 학습 스크립트와 디바이스에서 어긋나는 사고 —
온디바이스 AI 에서 가장 자주, 가장 늦게 발견되는 버그다.
여기서 계약을 하나로 묶어 두면 그 사고를 막을 수 있다.

## 실습

```bash
pytest -m lesson_1_7 -s
```

## 무엇을 보게 되는가

```text
모델 입력 계약 (curated)
  input_shape     : (30, 6)  (원소 180개)
  feature_fields  : active_power_kw, reactive_power_kvar, current_a, voltage_v,
                    temperature_c, spindle_rpm
  label_field     : condition
  normalization   : ZSCORE (통계 출처: train)
  window          : 300초를 한 덩어리로
```

`(30, 6)` — 30 표본 × 6 채널.
10초 주기이므로 한 표본이 현장 시간 **300초**를 본다.

## 넣으면 안 되는 것을 설계 단계에서 막는다

```python
spec(feature_fields=("batch_id", ...))    # InvariantViolation: 그 묶음을 외운다
spec(feature_fields=("condition", ...))   # InvariantViolation: 정확도 100% 짜리 쓸모없는 모델
spec(feature_fields=("timestamp", ...))   # InvariantViolation: 배포 즉시 분포가 벗어난다
```

이 셋의 공통점: **전부 검증 점수를 올린다. 그리고 전부 현장에서 무너진다.**

| 넣으면 | 무슨 일이 일어나는가 |
|--------|----------------------|
| `IDENTIFIER` | 모델이 패턴이 아니라 ID 를 외운다 |
| `GROUP` (LOT/설비) | 모델이 공정이 아니라 그 묶음을 외운다 |
| `LABEL` | 정확도 100%. 배포하면 그 열이 없다 |
| `TIME_INDEX` | 학습 구간의 시각만 아는 모델. 다음 날 바로 분포 밖 |

실습 1-3 에서 정한 `FieldRole` 이 여기서 값을 한다.
역할을 대충 정했다면 이 방어가 작동하지 않는다.

## 정규화 통계는 train 에서만

```bash
# 분할 없이 통계를 뽑으려 하면
UnsupportedOperation: 분할이 없다. 정규화 통계는 train 분할에서만 뽑을 수 있으므로
                      데이터를 먼저 나눠야 한다.
```

전체 데이터로 평균과 표준편차를 구하면, 그 안에는 test 의 정보가 섞인다.
모델은 시험 문제의 평균을 미리 알고 시험을 보는 셈이 되고,
검증 점수는 올라가지만 현장 성능은 그대로다.

**가장 잡기 어려운 종류의 누수다.** 코드 어디에도 버그가 없어 보이기 때문이다.

이 규칙은 Use Case 가 아니라 Value Object 가 지킨다.

```python
NormalizationSpec(method=ZSCORE, fitted_on="all", statistics={...})
# InvariantViolation: 정규화 통계를 'all' 에서 뽑았다. train 이 아니면 데이터 누수다.
```

## 커리큘럼 순서와 엔지니어링 순서

실습 순서는 1-7(설계) → 1-8(분할)이지만,
**정규화 통계를 뽑으려면 분할이 먼저**다.

그래서 실습은 이렇게 진행된다.

1. 정규화 없이 설계한다 → `SPEC_NO_NORMALIZATION` 경고가 남는다
2. 분할한다 (실습 1-8)
3. 같은 설계를 `fit_normalization=True` 로 다시 한다 → 경고가 사라진다

같은 종류의 검사를 다시 하면 **덮어쓴다.** 재검사가 가능해야 데이터를 고칠 수 있다.

## train 구간에서 계산한 값

```text
  active_power_kw        mean=   151.627  std=   35.829
  current_a              mean=   251.572  std=   63.328
  voltage_v              mean=   380.013  std=    2.218
  temperature_c          mean=    26.057  std=    2.406
```

정규화 없이 이 값들을 그대로 넣으면 어떻게 되는지 보라.
전류(약 250)와 온도(약 26)는 스케일이 10배 다르다.
경사 하강법은 값이 큰 축을 먼저 줄인다.

## 이미지의 경우

```python
ImageInputSpec(width=224, height=224, channels=3)
# input_shape == (3, 224, 224)   ← PyTorch 관례
# input_element_count == 150,528
```

이 숫자가 모듈 4(최적화)에서 그대로 이어진다.
입력 크기를 절반으로 줄이면 연산량이 1/4이 된다. 그 판단의 출발점이 여기다.

## 창이 과하게 겹치면

```python
WindowSpec(length=100, stride=1, ...)   # overlap_ratio = 0.99
# WARNING SPEC_WINDOW_OVERLAP_HIGH
```

거의 같은 표본이 대량 복제된다. 데이터가 100배 늘어난 것처럼 보이지만
실제 정보량은 그대로고, 검증 점수만 부풀려진다.

## 자주 하는 실수

- **`StandardScaler().fit(전체)` 후 split.** 이 한 줄이 가장 흔한 누수다.
- **window 길이를 성능 보고 정한다.** 성능이 잘 나오는 길이가 아니라,
  현장에서 이상이 드러나는 길이여야 한다.
- **전처리를 학습 코드에 인라인으로 쓴다.** 디바이스에 배포할 때 그 코드를 다시 짜게 되고,
  두 구현이 미묘하게 달라진다.
