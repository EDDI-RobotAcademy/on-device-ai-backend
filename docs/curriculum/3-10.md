# 3-10. 현장 데이터를 통과하는 모델만 살아남는다

## 문제

학습이 끝났다고 모델이 완성된 것이 아니다.
**"검증 정확도가 제일 높은 모델"과 "현장에 내보낼 수 있는 모델"은 다르다.**

```text
모듈 1  이 데이터가 무엇인지 아는가
모듈 2  이 데이터가 쓸 만한가
모듈 3  이 **모델**이 쓸 만한가
```

## 실습

```bash
pytest -m lesson_3_10 -s
```

## 정확도 97% 모델이 막힌다

```text
모델 승인 판정: FAILED  (mv-acc-overlap-cnn1d-s42)
  정확도 0.974 / macro recall 0.949 / p95 0.12ms

차단 사유:
  ✗ CRITICAL PROTOCOL_SPLIT_OVERLAP (split) 분할 사이에 40 개 표본이 겹친다.
                                            창이 겹치면(실습 3-4) 나눠도 겹친다.
```

정확도 97.4%. 나쁘지 않은 숫자다.
그런데 분할 경계에서 **40 표본이 새고 있었다**(실습 3-8).

**그 정확도는 시험 문제를 일부 보고 낸 점수다. 숫자 자체를 믿을 수 없다.**

## 겹침을 없앤 모델은 통과한다

```text
모델 승인 판정: PASSED  (mv-acc-disjoint-cnn1d-s42)
  정확도 1.000 / macro recall 1.000 / p95 0.13ms

  ✓ 막는 것도, 걸리는 것도 없다.
```

그런데 여기에도 읽어야 할 것이 있다.

> 평가 표본이 **66개**다 — 겹치는 쪽은 195개였다.
> 66개로 낸 정확도 100% 를 얼마나 믿을 것인가.

**이것이 겹침을 없앤 대가다.**
정직한 66개와 오염된 195개 중 무엇이 나은가 — 정직한 쪽이다.
다만 그 66개가 얇다는 사실도 함께 보고해야 한다.

## 승인 판정이 보는 네 가지

```python
@dataclass(frozen=True, slots=True)
class ModelAcceptancePolicy:
    learning: LearningPolicy          # 1. 학습이 실제로 일어났는가      (3-6)
    overfitting: OverfittingPolicy    # 2. 외운 것이 아닌가              (3-7)
    protocol: EvaluationProtocol      # 3. 평가가 정직한가               (3-8)
    evaluation: EvaluationPolicy      # 4. 정확도 뒤에 실패가 없는가      (3-9)
    latency: LatencyBudget | None     # 5. 시간 안에 도는가              → 모듈 4
    require_gates: bool = True        # 0. 게이트를 통과한 데이터인가     (1, 2)
```

앞의 아홉 실습에서 만든 규칙이 **여기 한 곳에 모인다.**

## 지연시간 예산 — 정확도와 같은 저울에 올릴 수 없다

```text
모델 승인 판정: FAILED
차단 사유:
  ✗ CRITICAL ACCEPT_LATENCY_OVER_BUDGET (latency)
    p95 지연시간 0.13ms 가 예산 0.01ms 를 넘는다.
    정확도와 무관하게 이 모델은 현장에서 못 쓴다.
```

```python
@dataclass(frozen=True, slots=True)
class LatencyBudget:
    """디바이스에서 허용되는 시간.

    이 숫자는 모델이 정하는 것이 아니다. **현장의 사이클 타임이 정한다.**
    30ms 라면, 그것은 설비가 30ms 마다 판단을 요구한다는 뜻이다.
    """
    p95_ms: float
```

정확도는 그대로다. 그런데 못 쓴다.
**둘 다 통과해야 한다** — 하나를 다른 하나로 상쇄할 수 없다.

이 예산을 맞추는 일이 모듈 4(최적화) 전체다.

## 현장 홀드아웃 — 다른 날 데이터

```text
현장 홀드아웃 (이틀 뒤 12시간)
평가 (run-clean) — field
...
test 정확도 100.0% → 현장 정확도 ...%
```

test 분할은 같은 36시간에서 나온다. **같은 날, 같은 조건이다.**
"현장에서 살아남는가"는 **다른 날 데이터로만** 답할 수 있다.

```python
field_data = replace(
    run.data,
    dataset_ref=f"{run.data.dataset_ref}/field",
    uri=command.field_uri,
)
```

`replace` 로 **uri 만** 바꾼다. 나머지는 그대로다 — 특히 정규화 통계.

> 정규화 통계는 학습 때 쓰던 값을 그대로 쓴다(실습 1-7).
> 현장 데이터로 다시 뽑으면 그건 배포된 모델과 다른 전처리다.

이 한 줄이 배포 사고의 큰 몫을 막는다.

## 판정된 모델은 몰래 바뀌지 않는다

```python
IllegalStateTransition: ACCEPTED 상태에서는 평가를 다시 기록할 수 없다.
                        reopen(reason) 으로 판정을 되돌린 뒤 수정한다.
```

모듈 1의 `Dataset.reopen`, 모듈 2의 `QualityAssessment.reopen` 과 같은 구조다.
되돌리려면 이유를 남겨야 하고, 그 기록이 감사 근거가 된다.

## 세 게이트

```text
[모듈 1] 학습 착수 판정      READY
[모듈 2] Data Quality Gate   PASSED
[모듈 3] 모델 승인 판정       PASSED
                              ↓
                         배포 (모듈 5)
```

각 게이트는 **다른 질문**을 하고, 앞의 게이트를 통과했다고 뒤가 통과되지 않는다.
그리고 세 게이트 모두 같은 형태를 갖는다.

```text
측정(Infrastructure) → 판정(Domain Policy) → 인증서(Certificate) → 이벤트
```

## API 로 해보기

```bash
# 1. 준비 (게이트 확인 + 텐서 + 구조 프로파일)
curl -X POST localhost:8000/training-runs -d @prepare.json

# 2. 시작 — 202 가 즉시 돌아온다
curl -X POST localhost:8000/training-runs/run-1/start

# 3. 진행 상황
curl localhost:8000/training-runs/run-1
curl localhost:8000/training-runs/run-1/curve

# 4. 평가
curl -X POST localhost:8000/training-runs/run-1/evaluations \
     -d '{"split": "test", "policy": {"critical_labels": ["FAULT"]}}'

# 5. 현장 홀드아웃
curl -X POST localhost:8000/training-runs/run-1/field-evaluations \
     -d '{"field_uri": "data/samples/plant_power_model_field.csv"}'

# 6. 승인 판정
curl -X POST localhost:8000/training-runs/run-1/acceptance \
     -d '{"split": "field", "latency_p95_ms": 30.0,
          "evaluation": {"critical_labels": ["FAULT"], "min_critical_recall": 0.9}}'
```

전체 흐름은 [`api-examples.http`](../../api-examples.http) 에 있다.

## 자주 하는 실수

- **가장 정확한 모델을 고른다.** 놓치면 안 되는 것을 놓치는지부터 본다.
- **test 정확도로 배포를 결정한다.** 같은 날 데이터다. 다른 날로 한 번 더 봐야 한다.
- **지연시간을 나중에 잰다.** 예산을 못 맞추면 정확도가 아무리 좋아도 못 쓴다.
- **승인 기준을 모델에 맞춰 조정한다.** 기준은 현장이 정하고, 모델이 거기 맞춰야 한다.

## 모듈 3 을 마치며

열 개의 실습이 하나의 Bounded Context 를 만들었다.

```text
domain/model/
├── training_run.py      Aggregate Root — 준비 → 학습 → 평가 → 판정
├── training_data_ref.py 앞 두 모듈의 게이트 통과 증거를 담은 VO   (3-1)
├── tensor_spec.py       AI가 먹는 모양                            (3-1, 3-3)
├── architecture.py      어떤 계산을 하는가, 얼마나 무거운가        (3-2)
├── windowing.py         시간을 어디서 끊는가                      (3-4)
├── training_config.py   무엇을 재현할 수 있어야 하는가            (3-5)
├── curve.py             배우고 있는가, 외우고 있는가              (3-6, 3-7)
├── protocol.py          평가가 정직한가                           (3-8)
├── evaluation.py        정확도 뒤에 무엇이 있는가                 (3-9)
└── acceptance.py        현장에 내보낼 수 있는가                   (3-10)
```

이 Context 에 **`torch` 라는 단어가 하나도 없다.**
PyTorch 는 `infrastructure/ml/` 안에서만 산다. 그 경계를 테스트가 지킨다.

```bash
pytest tests/test_architecture.py -k PyTorch
```
