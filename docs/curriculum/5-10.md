# 5-10. 망가진 모델을 Rollback하라

## 문제

이 실습의 설계 결정 하나가 나머지를 전부 설명한다.

> **롤백은 되돌리기가 아니라 새 배포다.**

v3 에서 v1 로 돌아가면 결과는 **v4** 다 (내용은 v1).
버전 번호는 줄어들지 않는다.

## 실습

```bash
pytest -m lesson_5_10 -s
```

## 무엇을 보게 되는가

```text
배포 dep-line3  3라인 전력 감시 [DEVICE_GROUP · 3대]  → ROLLED_BACK
--------------------------------------------------------------------------
  v1   2026-05-19 23:00:00  mv-power-opt-cnn1d-s42 (TFLITE/FP32)
  v2   2026-05-21 12:00:00  mv-power-opt-cnn1d-s42 (TFLITE/INT8)
  v3   2026-05-22 12:00:00  mv-power-opt-cnn1d-s42 (ONNX/FP32)
  v4   2026-05-23 09:00:00  mv-power-opt-cnn1d-s42 (TFLITE/FP32)  ← v3 에서 롤백
```

## 번호를 되감지 않기 때문에 시간에 답할 수 있다

**이것이 새 버전을 만드는 이유의 전부다.**

```text
2026-05-20 12:00:00 → v1 (TFLITE/FP32)
2026-05-21 18:00:00 → v2 (TFLITE/INT8)
2026-05-22 18:00:00 → v3 (ONNX/FP32)
2026-05-23 12:00:00 → v4 (TFLITE/FP32)
```

번호를 v1 로 되감았다면 `5-22 18시` 와 `5-23 12시` 를 구분할 수 없다.
둘 다 v1 이 되기 때문이다.

그러면 그 시각의 로그를 봐도 "어느 v1 이었는지" 모른다.
[5-2](5-2.md) 의 `version_at()` 도, [5-3](5-3.md) 의 `deployment_version` 도 무의미해진다.

```python
version = DeploymentVersion(
    number=from_version + 1,          # **줄이지 않는다**
    artifact=source.artifact,         # 내용은 v1 의 것
    released_at=occurred_at,
    note=reason.strip(),
    rolled_back_from=from_version,    # 어디서 돌아왔는지
)
```

## 돌아갈 곳이 없으면 롤백이 아니다

```text
[DEPLOYMENT_VERSION_NOT_FOUND] v7:
    v7 은 이 대상에 배포된 적이 없다. 돌아갈 곳이 없으면 롤백이 아니다.
```

`version_of(n)` 이 없으면 막는다.
**"어딘가 있을 v7"** 로 되돌리는 일은 일어나지 않는다.

첫 배포 직후에는 항상 이 상황이다.
그래서 첫 배포는 좁게 한다 ([5-1](5-1.md)) — 그때 할 수 있는 건 격리뿐이기 때문이다.

## 이유 없는 롤백은 아무것도 알려주지 않는다

```text
[INVARIANT_VIOLATION] reason:
    이유 없는 롤백은 다음 사람에게 아무것도 알려주지 않는다.
```

`"일단 되돌림"` 이라고 적힌 기록은 반년 뒤에 아무 도움이 안 된다.
그리고 그 이유는 **버전의 note 로 남는다** — 이력을 읽으면 바로 보인다.

## 격리 → 원인 확인 → 롤백

```text
2026-05-23 09:00:00  격리 — 05-23 16시: CRITICAL OPS_INPUT_OUT_OF_RANGE ...
2026-05-23 10:00:00  v4 롤백 (v3 → v1 의 내용) — 입력 드리프트 확인, v1 로 복귀
```

격리된 상태에서도 롤백은 된다. 순서가 자연스럽다.

```text
멈춘다(격리) → 원인을 본다 → 되돌린다(롤백)
```

롤백이 되면 격리 사유는 해소된 것으로 본다 — 다른 모델이 돌기 시작했기 때문이다.

## 롤백해도 나아진다는 보장은 없다

**그래서 격리가 먼저다** ([5-8](5-8.md)).

```text
새 모델 자체가 나빴다      → 롤백이 듣는다
세상이 변했다 (입력 드리프트) → **v1 도 그 입력을 본 적이 없다**
```

이 실습의 v1 과 v3 는 같은 학습 데이터에서 나왔다.
형식만 다를 뿐(TFLITE/FP32 vs ONNX/FP32) **배운 것은 같다.**

입력이 학습 범위를 벗어난 것이라면([5-7](5-7.md)) 롤백은 아무것도 고치지 못한다.
그때 필요한 것은 재학습이다 ([5-11](5-11.md)).

## 사건 조사는 이력부터 읽는다

```text
2026-05-19 23:00:00  v1 배포 — ...-tflite-fp32 (TFLITE/FP32, 16,780B)  기준 p95 0.0032ms
2026-05-21 12:00:00  v2 배포 — ...-tflite-int8 (TFLITE/INT8, 9,512B)   기준 p95 0.0038ms
2026-05-22 12:00:00  v3 배포 — ...-onnx-fp32   (ONNX/FP32, 14,169B)    기준 p95 0.0085ms
2026-05-23 09:00:00  v4 롤백 (v3 → v2 의 내용) — ONNX 런타임 메모리 초과
```

**언제 무엇을 왜 했는가**가 한 표에 있다.

## 같은 버전으로는 돌아갈 수 없다

```text
[ILLEGAL_STATE_TRANSITION] dep-line3: 이미 v3 이 돌고 있다.
```

아무 일도 안 하는 롤백이 기록에 남으면, 그 이력은 읽는 사람을 속인다.

## API

```http
POST /deployments/dep-line3/rollback
{
  "to_version": 1,
  "reason": "v3 배포 후 FAULT 재현율 붕괴",
  "occurred_at": "2026-05-23 09:00:00"
}
```

응답의 `current_version` 은 **4** 다. 1 이 아니다.

## 자주 하는 실수

- **버전 번호를 되감는다.** 그 시간의 기록이 사라진다.
- **이유를 안 적는다.** 반년 뒤에 아무도 모른다.
- **격리 없이 바로 롤백한다.** 이전 모델도 같은 입력을 본 적이 없다.
- **롤백으로 드리프트를 고치려 한다.** 그건 재학습으로만 고쳐진다.
