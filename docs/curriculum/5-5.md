# 5-5. Latency가 무너지면 무엇이 달라졌는가?

## 문제

모델은 안 바뀌었다. 바이트 하나 안 바뀌었다.
그런데 현장 p95 가 벤치마크의 24배가 됐다.

**바뀐 것은 환경이다.** 그 사실을 아는 것이 조치의 출발점이다.

## 실습

```bash
pytest -m lesson_5_5 -s
```

## 현장은 원래 벤치마크보다 느리다

```text
벤치마크(모듈 4) p95 : 0.0031ms
1일차 현장       p95 : 0.0297ms      ← 10배. **이건 정상이다.**
4일차 현장       p95 : 0.0747ms      ← 거기서 또 2.5배. 이쪽이 사건이다.
```

PC 와 임베디드 CPU 는 원래 다르다. 그래서 예산에 여유를 둔다.
`max_regression_ratio` 가 1.0 이 아닌 이유다 — 1.0 을 요구하면 첫날부터 알람이 울린다.

**"느려졌다"를 말하려면 두 숫자가 필요하다.** 벤치마크와 현장. 앞의 것은 모듈 4 에서 온다.

## 전부가 아니라 한 대다

```text
4일차 마지막 창 — 디바이스별 p95
  DEV-01        0.0291ms
  DEV-02        0.0798ms      ← 2.9배
  DEV-03        0.0279ms
```

**평균은 이것을 숨긴다.** 세 대를 뭉쳐 재면 p95 가 0.0747ms 로 나오고,
"전체적으로 느려졌다"고 읽게 된다.

| 관측 | 의심할 곳 |
|---|---|
| 세 대가 같이 느려졌다 | 모델, 배포, 공통 환경 |
| **한 대만 느려졌다** | 그 디바이스 — 팬 고장, 발열, 다른 프로세스, 전원 정책 |

디바이스를 로그에 안 남겼으면([5-3](5-3.md)) 이 구분을 할 수 없다.

```python
# 창을 디바이스별로 자른다
slice_windows(records, hours=8, device_id="DEV-02")
```

## 모델을 의심하기 전에 환경을 의심한다

```text
WARNING OPS_LATENCY_REGRESSION
        벤치마크의 24.2배로 느려졌다.
        **모델은 안 바뀌었다** — 발열, 다른 프로세스, 전원 정책,
        밀린 큐 중 하나를 의심한다.  [측정 24.19 / 기준 12]
```

의심할 곳은 넷이다.

```text
발열로 클럭이 내려갔다        (thermal throttling)
다른 프로세스가 코어를 가져갔다
큐가 밀려 입력이 쌓였다
전원이 절전 모드로 들어갔다
```

이 소견의 메시지에 "모델은 안 바뀌었다"가 들어 있는 이유다.
현장에서 지연시간이 무너지면 **먼저 모델을 되돌리려 한다.** 대개 잘못된 조치다.

## 느려진 것과 못 지키는 것은 다르다

```text
20배 느려졌지만 사이클 안 → WARNING
사이클을 넘김              → CRITICAL — 설비가 부품을 기다리기 시작한다
```

```python
if profile.p95_ms > self.cycle_budget_ms:
    findings.append(Finding(code="OPS_OVER_CYCLE_BUDGET", severity=Severity.CRITICAL, ...))
```

`cycle_budget_ms` 는 모듈 4 의 `DeviceBudget.latency_p95_ms` 와 **같은 숫자여야 한다.**
배포 전에 지킨 예산을 배포 후에 다른 숫자로 재면 그 예산은 의미가 없다.

## 끝나지 않은 추론은 분위수에 안 잡힌다

```text
CRITICAL OPS_TIMEOUT
         추론 12건이 아예 끝나지 않았다.
         이 건들은 지연시간 분포에 안 잡힌다 — p95 만 보면 안 보인다.
```

```python
# 타임아웃은 분위수에서 뺀다. **끝나지 않은 추론에는 지연시간이 없다.**
over = values > self._timeout_ms
timeouts = int(over.sum())
values = values[~over]
```

p95 4ms 짜리 창에서 12건이 아예 안 끝났다면, 그 창은 좋은 창이 아니다.
**따로 세지 않으면 없는 일이 된다.**

## 평소엔 괜찮은데 가끔 튄다

```text
WARNING OPS_LATENCY_JITTER
        p95 가 p50 의 4.5배다.
        평소엔 괜찮은데 가끔 크게 튄다 — 대개 다른 작업과 겹치는 순간이다.
```

평균은 2ms 라고 말하지만 20번에 한 번은 9ms 다.
사이클 타임은 평균으로 지켜지지 않는다 (실습 4-1 과 같은 이야기다).

지터가 높으면 찾을 것은 모델이 아니라 **그 시각에 같이 도는 작업**이다.

## 측정은 Infrastructure, 판정은 Domain

```text
LogLatencyMeasurer     로그의 latency_ms 로 분위수를 낸다   ← 좋은지 나쁜지 말하지 않는다
      ↓
LatencyProfile         숫자 + 창
      ↓
LatencyPolicy.inspect  이 지연시간을 받아들일 것인가
```

`LatencyPolicy` 는 pandas 도 numpy 도 모른다.
그래서 숫자를 손으로 만들어 시험할 수 있다 — 이 실습의 절반이 그렇게 되어 있다.

## 자주 하는 실수

- **벤치마크와 현장을 같은 기준으로 잰다.** 첫날부터 알람이 울리고, 알람을 끈다.
- **전체 평균만 본다.** 한 대의 고장이 묻힌다.
- **지연시간이 무너지면 모델을 되돌린다.** 대개 환경 문제다.
- **타임아웃을 안 센다.** 가장 나쁜 건들이 통계에서 빠진다.
