# 4-6. FP16으로 줄이고 무엇을 얻었는지 확인하라

## 문제

FP16 은 숫자 하나를 4바이트 대신 2바이트로 쓴다.
그러니 파일이 절반이 되어야 한다 — **가 아니다.**

여기서 실제로 얻은 것과 잃은 것을 각각 센다.

## 실습

```bash
pytest -m lesson_4_6 -s
```

## 무엇을 보게 되는가

```text
FP32  파일  16,780B = 가중치  12,748 + 오버헤드   4,032
FP16  파일  11,724B = 가중치   6,374 + 오버헤드   5,350
```

가중치는 **정확히 절반**이 되었다 (12,748 → 6,374).
그런데 파일은 **70% 로만** 줄었다.

**오버헤드가 4,032B → 5,350B 로 오히려 늘었기 때문이다.**
FP16 변환은 각 텐서에 스케일 정보를 함께 담는다. 그 몫이 추가된다.

## 값은 흔들리고 답은 그대로다

```text
FP32 : max|diff| 1.907e-06   argmax 일치 100.00%
FP16 : max|diff| 1.008e-03   argmax 일치 100.00%
```

`max|diff|` 가 1e-06 대에서 **1e-03 대로 커졌다.** 값은 분명히 흔들렸다.
그런데 어느 클래스가 가장 큰지는 바뀌지 않았다.

## 허용 오차는 정밀도마다 다르다

```python
def tolerance_for(self, precision: Precision) -> float | None:
    """INT8 은 값 자체를 비교하지 않는다. 애초에 다른 숫자를 쓰기 때문이다."""
    if precision is Precision.FP32:
        return self.max_abs_diff_fp32   # 1e-4
    if precision is Precision.FP16:
        return self.max_abs_diff_fp16   # 1e-2
    return None                          # INT8
```

FP16 을 FP32 기준(1e-4)으로 재면 **전부 실패한다.**
그러면 아무도 이 검사를 쓰지 않게 되고, 검사는 있으나 마나가 된다.

**기준이 현실과 맞지 않으면 검사는 꺼진다.** 그것이 검사를 없애는 가장 흔한 방식이다.

## 작아졌다고 빨라지는 것은 아니다

```text
TFLITE/FP32  p50 0.0030ms  p95 0.0031ms
TFLITE/FP16  p50 0.0030ms  p95 0.0030ms
```

거의 그대로다.

이 CPU 에는 FP16 연산기가 없다.
그래서 인터프리터는 **FP16 으로 저장된 가중치를 FP32 로 풀어서** 계산한다.

| 얻은 것 | 못 얻은 것 |
|---|---|
| 파일 크기 (플래시) | 연산 속도 |
| 메모리 대역폭 | |

디바이스에 FP16 유닛이 있으면 그때 속도도 따라온다.
**하드웨어를 모르면 이 변환의 값어치를 계산할 수 없다.**

이 이야기는 [4-9](4-9.md) 에서 정확히 설명된다 —
메모리 병목인 층에서는 데이터가 절반이 되는 것만으로도 빨라지고,
연산 병목인 층에서는 아무 일도 일어나지 않는다.

## 변환 설정은 두 줄이다

```python
converter.optimizations = [tf.lite.Optimize.DEFAULT]
converter.target_spec.supported_types = [tf.float16]
```

INT8 과 달리 **대표 데이터가 필요 없다.**
FP16 은 값의 범위를 몰라도 되기 때문이다 — 지수부가 있는 부동소수점이므로 그대로 줄이면 된다.

이 차이가 [4-7](4-7.md) 의 출발점이다.

## 자주 하는 실수

- **파일이 절반이 될 것이라고 약속한다.** 오버헤드는 안 줄고 오히려 는다.
- **FP16 을 양자화라고 부른다.** 정수로 바꾸지 않았다.
- **속도를 기대한다.** 하드웨어가 FP16 을 지원해야 빨라진다.
- **FP32 기준으로 동등성을 판정한다.** 전부 실패하고, 결국 검사를 끄게 된다.
